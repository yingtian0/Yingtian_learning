# 第10回 演習

すべて Go(標準ライブラリのみ)。5本は、1つのモジュール(`ex10net`)にまとめてある。macOS(Apple Silicon)で動作を確認した。**Linux での実行は未確認**。

```bash
cd 10-dns-cdn-and-load-balancing/exercises
go run ./ex1_dns
go run ./ex2_lb_algorithms
go run ./ex3_proxy
go run ./ex4_bgp_sim
go run ./ex5_cdn_cache
```

| 演習 | 実体 |
|---|---|
| ex1 | **ループバックの自作の DNS サーバー 3 台**(ルート、TLD、権威)と、自作の再帰リゾルバ。実在の DNS サーバーには、問い合わせない |
| ex2 | シミュレーション(キューイングのモデル、ハッシュ) |
| ex3 | **ループバックの、実際の HTTP サーバーと、実際のプロキシ**(L4、L7) |
| ex4 | シミュレーション(13 個の AS の、簡易 BGP) |
| ex5 | A、B はシミュレーション。C は、ループバックの実際の HTTP のオリジンと、自作のキャッシュ |

## 進め方

第1〜9回と同じ。実行前に予想を書き、実行して比べ、外れたら理由を調べる。

**注意(安全のため)**

- **すべて、自分のマシンの中(ループバックと、メモリ内)で完結する**。実在の DNS サーバー、CDN、BGP のルーター、他人のサーバーには、接続しない。
- ex1 の名前は、予約された `.test`、アドレスは、文書用の範囲(192.0.2.0/24、203.0.113.0/24)。
- **ex4(BGP)のシミュレーションは、実際のインターネットのルーターに、経路を広告する道具ではない**。乗っ取りやリークは、概念を理解するための、**メモリ内のモデル**である。現実のインターネットで、他人のプレフィックスを広告することは、重大な障害を起こし、**絶対にしない**。
- 実在のドメインや、他人のサーバーに対して、`dig +trace` などで、大量の問い合わせをする改造は、**控えめな頻度**で、**自分が管理するもの**にだけ行う。
- **ex3 は、CPU を使い切る**。他の作業を止めてから実行する。

## 演習1: DNS

[ex1_dns/](ex1_dns/)(`dns.go`: メッセージの符号化と復号、`main.go`: サーバー、リゾルバ、実験)

**課題**

1. A の、16進のダンプを、**自分の手で読む**。フラグの `0x0100`、`0x8500` を、ビットに分解して、意味を言う。
2. C の 10 個の結果を、表にして、**各段階の、往復の回数と、時間**を、各サーバーの RTT(10、30、60 ms)から、**予測する**。実測と、一致するか。
3. **改造**: ルート → TLD → 権威の、RTT を変える(例えば、権威を 200 ms に)。冷えた解決と、キャッシュ後の差は、どうなるか。
4. **改造**: **キャッシュなしのリゾルバ**(毎回、ルートから)と、キャッシュありを、100 個の名前で比べる(同じゾーンの、異なる名前)。NS のキャッシュだけが、ある場合と、全くない場合で、全体の時間は。
5. **改造**: **リゾルバのキャッシュに、TTL の上限と下限**を設ける(`min-ttl = 10 秒`、`max-ttl = 60 秒`)。短い TTL(2 秒)の名前の、挙動は、どう変わるか。(実際のリゾルバや、アプリが、TTL を無視する場合の、影響を考える。)
6. **改造**: 権威サーバーが、**応答しない**(パケットが失われる)場合の、**再送とタイムアウト**を実装する。複数の権威サーバーがあるとき、**次のサーバーに切り替える**。タイムアウトを、1 秒、2 秒にしたときの、解決の遅延は。
7. **改造**: **EDNS0**(OPT レコード)を実装し、UDP の最大の大きさを、4096 バイトに広げる。大きな応答(TXT 12 件、約 1.4 KB)が、**UDP で収まる**ようになり、**TCP のやり直しが、不要**になる。時間は、183 ms から、約 61 ms に戻るか。
8. **改造**: **ラウンドロビン DNS** を実装する。同じ名前に、複数の A レコードがあり、応答のたびに、順序を回す。リゾルバは、キャッシュするので、**クライアントには、同じ順序で返る**ことを確認する。
9. **改造**: **ヘルスチェック連動**: 権威サーバーが、バックエンドの死活を見て、**故障したアドレスを、答えから外す**。TTL が 60 秒のとき、故障後、**何秒間**、古い答えが、リゾルバに残るか。
10. 発展: **DNSSEC の簡易版**を作る。各 RR に、HMAC の署名を付け、リゾルバが検証する。応答が、どれだけ大きくなるか。改ざんされた応答を、検出できるか。

## 演習2: ロードバランシングのアルゴリズム

[ex2_lb_algorithms/](ex2_lb_algorithms/)

**課題**

1. A の結果を、表にする。**裾の重い分布で、ラウンドロビンが崩れる**ことを確認する。**ランダムとラウンドロビンが、ほぼ同じ**になる理由を考える。
2. **改造**: サーバーの台数を、10 から 100 に変える(稼働率は同じ)。**最小接続と P2C の差は、どうなるか**(台数が多いほど、「2 台を見る」と「全台を見る」の差が、変わる)。
3. **改造**: P2C を、**d 個選ぶ**(d = 1、2、3、5、10)に一般化する。**d = 1 はランダム、d = 台数は最小接続**。**d = 2 で、改善のほとんどが得られる**ことを、確認する。(Mitzenmacher の結果。)
4. **改造**: サーバーの能力が、**不均一**(半分が 2 倍速い)なとき、各方式は、どうなるか。**加重ラウンドロビン**を実装して、比べる。
5. **改造**: **古い情報**で振り分ける。最小接続が、**100 リクエスト前**の状態を見て決める場合(情報の遅れ)。**空いているサーバーに、リクエストが殺到する**(herd 効果)ことを確認する。P2C は、これに強いか。
6. **改造**: B の、一貫性ハッシュで、**サーバーを 1 台、順に足していく**(10 → 11 → 12 → … → 20)。**累積の移動の量**と、**負荷の偏り**を測る。
7. **改造**: **有限の負荷の一貫性ハッシュ**(bounded-load consistent hashing)を実装する。各サーバーの負荷に、上限(平均の 1.25 倍)を設け、超えたら、リング上の次のサーバーへ。偏りは、どう変わるか。
8. 発展: **Maglev ハッシュ**を実装する。サーバーの追加で、移動の割合が、どうなるか。一貫性ハッシュと、**偏りと移動のトレードオフ**を、比べる。

## 演習3: ロードバランサ(リバースプロキシ)

[ex3_proxy/](ex3_proxy/)

**課題**

1. A の 4 経路の、リクエスト/秒と、遅延を、表にする。**L4 と L7 の、スループットの比**(約 57% 対 32%、直接に対して)を、計算する。
2. **改造**: バックエンドの処理時間を、0 から 1 ms、10 ms に変える。**プロキシのオーバーヘッドが、相対的に小さくなる**ことを確認する。
3. **改造**: **クライアントの並行数**を、1、8、32、128 と変える。L4 と L7 の、スループットと p99 は、どう変わるか。
4. **改造**: **TLS を終端する L7 プロキシ**(第9回の `internal/pki` を使う)を作る。クライアントとプロキシの間を TLS にして、プロキシとバックエンドの間を平文にする。**TLS の終端のコスト**は、どれだけか。
5. **改造**: **HTTP/2** で、クライアントとプロキシの間を、1 本の接続にする。**接続単位の L4 プロキシ**では、**負荷が、バックエンドに、偏る**ことを確認する(1 本の接続は、1 台に固定される)。
6. **改造**: B の、**P2C** を、`lbTransport` に追加する。最小接続と、**遅いサーバーへの、振り分け**を比べる。
7. **改造**: C で、**アクティブなヘルスチェック**を実装する(1 秒ごとに、各バックエンドに、確認のリクエストを送る)。パッシブなものと比べて、**検出までの時間**は、どう違うか。
8. **改造**: **再試行の予算**を実装する(全リクエストの 10% まで)。バックエンドが、**全部遅い**(過負荷)とき、**再試行の嵐**が、予算で、抑えられることを確認する。再試行の予算がない場合と、比べる。
9. **改造**: **ドレイン**を実装する。バックエンドを外すとき、新しいリクエストは送らず、処理中の完了を待つ。外している間の、失敗は 0 か。
10. 発展: **アイドルタイムアウトの不一致**を再現する。バックエンドのタイムアウトを、プロキシより短くして、**502** が出ることを確認する(§3.7)。

## 演習4: BGP

[ex4_bgp_sim/](ex4_bgp_sim/)

**重要**: これは、**メモリ内のモデル**である。**実際のインターネットのルーターに、経路を広告する道具ではない**。

**課題**

1. シナリオ 1 の、各 AS の経路を、**自分で、手で、導く**(Gao–Rexford の規則から)。出力と、一致するか。
2. シナリオ 2 の、**どの AS が、攻撃者を選ぶか**を、「顧客/ピア/プロバイダ」の関係と、AS パスの長さから、説明する。**T3 が、S4 を選ぶ**理由は。
3. **改造**: 攻撃者を S1 から S5 に変える。7:4 の比は、どう変わるか。**攻撃者の位置(トポロジー上の)が、被害の範囲を決める**ことを確認する。
4. **改造**: 新しい AS を、足す(例えば、S1 と S5 の両方の顧客になる AS)。経路は、どう変わるか。**マルチホームの影響**。
5. **改造**: ROV を、**ランダムな AS の集合**に、10%、30%、50%、70% と、変えて、被害(攻撃者に流れる AS の数)を、グラフにする。**どの AS が、ROV を行うか**(最上位か、末端か)の違いは、どれだけ効くか。
6. **改造**: **AS パスの長さによる、攻撃**(経路の先頭に、正当な起点の AS 番号を、偽って付ける)を、実装する。ROV は、これを検出できるか。(ROV の限界。)
7. **改造**: **経路のリーク**を、別の AS(例えば、A2)で、起こす。被害は、どう変わるか。**リークの「タイプ」**(顧客 → プロバイダ、ピア → ピア)による違いは。
8. **改造**: エニーキャストで、**5 か所**から広告する。**各場所の分担の偏り**は、どうなるか。**最も近い場所**(ホップ数)と、実際に選ばれる場所は、一致するか。(BGP は、ホップ数ではなく、経済的な関係を優先する。)
9. **改造**: **収束の過程**を、観察する(`converge` の、ラウンドごとの変化を、表示する)。何ラウンドで、収束するか。広告の取り下げ(S3 が落ちる)の、収束は。
10. 発展: 公開されている、**実際の AS の関係のデータ**(CAIDA の AS Relationships データセット)を、読み込めるようにして、**実際のトポロジー**で、乗っ取りの影響を、シミュレートする。(データのダウンロードは、自分の責任で。)

## 演習5: CDN のキャッシュ

[ex5_cdn_cache/](ex5_cdn_cache/)

**課題**

1. A の、ヒット率の表を、グラフにする(横軸: キャッシュの大きさ、縦軸: ヒット率、α ごとに線)。**収穫が逓減する**ことを確認する。
2. **改造**: **時間で人気が変わる**アクセスを、生成する(例えば、1 時間ごとに、人気の順位を、ランダムに入れ替える)。**LFU が、LRU より悪くなる**ことを確認する。
3. **改造**: **ARC** または **TinyLFU** を実装して、LRU、LFU と比べる。(時間で人気が変わるアクセスで。)
4. **改造**: **one-hit wonder**(一度しか要求されない物件)を、全体の 40% 混ぜる。**admission**(2 回目の要求で、初めて、キャッシュに入れる)の効果を測る。
5. **改造**: **最適なキャッシュ**(Belady: 最も遠い未来に使われるものを追い出す)を実装して、上限とする。LRU、LFU との差は。
6. **改造**: B で、**エッジの数**を、2、8、32、128 と変える。**エッジが多いほど、エッジだけの構成では、オリジンへの要求が増える**ことを確認する。**共有層の効果は、エッジが多いほど、大きくなる**か。
7. **改造**: C で、**TTL の期限切れを、ずらす**(各物件の TTL に、ランダムなばらつき(ジッター)を加える)。**多数の物件が、同時に期限切れになり、オリジンに殺到する**ことが、避けられることを確認する。
8. **改造**: C の合流の実装に、**オリジンの失敗**(エラー、タイムアウト)を、加える。**失敗を、合流した全員に返す**のが、良いか。**古いものを返す**(stale-if-error)のが、良いか。
9. **改造**: C で、**200 個の要求を、異なる 200 個の物件**にする。合流は、何も助けないことを確認する。(合流が効くのは、**同じ物件**への要求。)
10. 発展: 実際の、アクセスログ(**自分の管理する、サーバー**のもの。または、公開されているトレース)を、読み込んで、実際のヒット率を測る。Zipf のモデルと、どれだけ、合っているか。
