# 第6回 演習

ex1〜ex4 は C(POSIX)。ex5 は Go。macOS(Apple Silicon)で動作を確認した。**Linux 用のコード(ex2 の `epoll`、ex3 の Linux の `sendfile`)は、書いてあるが、実行していない(未確認)**。`io_uring` と eBPF の演習は、この環境で動かせないため、課題としてのみ記す。

```bash
cd 06-kernel-and-io/exercises
```

## 進め方

第1〜5回と同じ。実行前に予想を書き、実行して比べ、外れたら理由を調べる。各計測は3回以上行う。

**注意**

- ex2 は、最大 5,000 本の接続を張り、約 25 秒かかる。ex5 に大きな数(1万以上)を渡すと、**エフェメラルポートが尽きる**ことがある(§本文 10)。
- ex2、ex3 は、直後に連続で実行すると、ポートの枯渇で失敗することがある。**しばらく待つ**(TIME_WAIT が消えるまで、約 30 秒)。
- ex3、ex4 は、512 MiB の一時ファイルを作る。

## 演習1: システムコールのコスト

[ex1_syscall_cost.c](ex1_syscall_cost.c)

```bash
cc -O2 -Wall -Wextra -o ex1 ex1_syscall_cost.c && ./ex1
```

**課題**

1. 各システムコールの、1回あたりの時間を表にする。関数呼び出しの何倍か。
2. `clock_gettime` が速い理由を調べる。Linux では、`strace -c ./ex1` で、`clock_gettime` が、システムコールとして**現れない**ことを確認する。
3. バッファの大きさと速度のグラフを作る。**どのサイズから、速度の伸びが鈍る**か。その理由を、固定のコストと、コピーの時間の関係で説明する。
4. **改造**: `pread` を、`read`(`lseek` で位置を動かす)に変えて比べる。`pread` が、1回のシステムコールで済む利点は。
5. **改造**: 小さなデータを `write` で 100 万回書く C のプログラムと、`fwrite`(stdio のバッファあり)で書くプログラムを比べる。`strace -c`(Linux)で、`write` の回数を見る。
6. **改造**: `readv`/`writev` で、複数の小さなバッファを、1回のシステムコールで送る。個別に `write` するより、どれだけ速いか。
7. 発展: Linux で、`strace -T` を使い、システムコール1回ごとの時間を見る。`strace` 自体が、プロセスを大きく遅くすること(`ptrace` のコスト)を確認する。

## 演習2: エコーサーバー(threads / poll / kqueue)

[ex2_echo_servers.c](ex2_echo_servers.c)

```bash
cc -O2 -pthread -Wall -Wextra -o ex2 ex2_echo_servers.c && ./ex2
```

**課題**

1. 結果の表を、`poll` と `kqueue` の、接続数ごとの往復/秒のグラフにする。`poll` が、接続数に反比例して遅くなることを確認する。
2. threads が、5,000 接続で警告を出す理由を説明する。この環境のスレッド数の上限は、どこで確認できるか(`sysctl kern.num_taskthreads`、Linux では `ulimit -u` と `/proc/sys/kernel/threads-max`)。
3. **改造**: スレッドのスタックの大きさ(`pthread_attr_setstacksize(&a, 64 * 1024)`)を、デフォルト(消す)にして、サーバーのメモリ(RSS)と、作れるスレッド数を比べる。仮想メモリの予約と、常駐メモリの違いを考える。
4. **改造**: 活発な接続を、10 本から 100 本、1,000 本に増やして、poll と kqueue の差を比べる。**すべての接続が活発なとき、`poll` の O(n) は、目立たなくなるか**。
5. **改造**: kqueue のサーバーを、**複数のスレッド**(スレッドごとに別の kqueue)に拡張する。`SO_REUSEPORT` で、複数のサーバーが同じポートを待ち受ける(macOS でも使える)。往復/秒は、スレッド数に応じて伸びるか。
6. **改造**: サーバーの `read` 後に、わざと 1 ms の `usleep` を入れる(遅いハンドラ)。単一スレッドのイベントループ(kqueue)と、threads で、全体の往復/秒がどう違うか。**1つの遅い処理が全体を止める**ことを確認する。
7. **Linux で実行できるなら**: `serve_event` の `epoll` 版が動くか確認する。**エッジトリガ**(`EPOLLET`)に変更して、読み切らないと接続が止まることを、わざとバグを作って確認する。
8. 発展: クライアントを複数プロセスにして、サーバーを飽和させ、3 つの流儀の、最大のスループットを比べる。

## 演習3: ゼロコピー

[ex3_zero_copy.c](ex3_zero_copy.c)

```bash
cc -O2 -Wall -Wextra -o ex3 ex3_zero_copy.c && ./ex3
```

**課題**

1. 3つの方法の、速度と、送信側の CPU(sys)を、3回測って、ばらつきを見る。
2. **送信側の CPU の差が、速度の差より大きいか**。ループバックでなく、実際のネットワーク(速度が遅い)では、何が変わるか、考える。
3. **改造**: read + write のバッファの大きさを、4 KiB、64 KiB、1 MiB と変えて、速度を比べる(演習1との関係)。
4. **改造**: データを**加工**する(例えば、全バイトに XOR する)read + write を追加する。sendfile は、この場合に、使えるか。
5. **Linux で実行できるなら**: `strace -c` で、システムコールの回数を比べる。`splice`、`MSG_ZEROCOPY` も試す。
6. **改造**: ファイルが、**ページキャッシュに載っていない**状態(最初の読み込み)で比べる。(macOS では `purge` が要り、管理者権限がいる。Linux では `echo 3 > /proc/sys/vm/drop_caches`。)方法の差は、どう変わるか。
7. 発展: 受信側も計測して、受信側の CPU を比べる。送信側のゼロコピーは、受信側には影響しないことを確認する。

## 演習4: mmap と read

[ex4_mmap_vs_read.c](ex4_mmap_vs_read.c)

```bash
cc -O2 -Wall -Wextra -o ex4 ex4_mmap_vs_read.c && ./ex4
```

**課題**

1. 順次とランダムの、結果の表を作る。mmap の1回目と2回目の差は、何によるか(ページフォルトの列を見る)。
2. 第2回の演習2と比べて、ページフォルトの回数が、**ファイルのサイズ ÷ ページサイズ**になっていることを確認する。
3. **改造**: `madvise(p, FSIZE, MADV_SEQUENTIAL)` や `MADV_WILLNEED` を、mmap の1回目の前に呼ぶ。1回目の速度は、どう変わるか。
4. **改造**: mmap の領域の、`sum_words` を、`MAP_POPULATE`(Linux)で事前にページフォルトを済ませた場合と比べる。
5. **改造**: ファイルのサイズを、メモリより大きくする(例えば 32 GiB。**空き容量に注意**)。ページキャッシュに載りきらないとき、mmap と read は、どう違うか。ページフォルトの種類は、マイナーかメジャーか。
6. **改造**: 別のプロセスが、mmap されているファイルを、`truncate` で縮める。mmap しているプロセスが、縮められた範囲に触れると、何が起きるか(`SIGBUS`)。
7. 発展: **書き込み**(`MAP_SHARED` で書く)と `pwrite` を比べる。mmap の書き込みは、いつ、ディスクに書かれるか(`msync`)。第5回の `fsync` との関係は。

## 演習5: Go のネットポーラ

[ex5_go_netpoller/](ex5_go_netpoller/)

```bash
cd ex5_go_netpoller
go run . 3000
```

**課題**

1. 3つの場面(A: ネットワークの `Read` で待つ、B: 生の `syscall.Read` で待つ、C: 活発な接続の往復)の、OS スレッドの数を比べる。
2. 暇な接続の数を、1,000、3,000、5,000 と変えて、A の OS スレッドの数と、スタック使用量が、どう変わるかを見る。**1 goroutine あたりのスタックは、約 2 KB** になるか。(1 万以上は、エフェメラルポートが尽きるので避ける。)
3. **B のパイプを、Go の `os.Pipe`(ネットポーラに登録される)に変えて**、`file.Read` で待つ。OS スレッドは、増えるか。**`syscall.Pipe` の生の fd と、何が違うか**。
4. **改造**: B で、`syscall.Read` を、**ディスク上のファイルの `Read`**(例えば、`/dev/zero` ではなく、大きなファイルを、大量の goroutine が同時に読む)に変えて、OS スレッドが増えることを確認する。セマフォ(バッファつきチャネル)で、同時数を制限すると、スレッドの増加が抑えられることを確認する。
5. **改造**: `debug.SetMaxThreads(100)` を設定して、B(200 個)を実行する。何が起きるか。
6. **改造**: C のクライアントを、別プロセスにして(サーバーとクライアントが、同じスケジューラを共有しないようにして)、往復/秒を、演習2と比べる。**演習2の kqueue(約 255,000 往復/秒)に、どこまで近づくか**。
7. **Linux で実行できるなら**: `strace -f -e trace=epoll_ctl,epoll_wait ./ex5` で、ネットポーラが、`epoll` を使っていることを確認する。`GODEBUG=schedtrace=1000` で、スケジューラの状態を見る。
8. 発展: Go のランタイムの `runtime/netpoll.go` を読み、`netpollblock`、`netpollready` が、goroutine を眠らせて、起こす部分を探す。

## 参考: この環境では実行できない演習

- **`io_uring`**: Linux のみ。`liburing` で、(a)ファイルの非同期の読み込み、(b)エコーサーバー(SQE で `accept`、`recv`、`send` を提出)を書き、演習2の `epoll` 版と比べる。`SQPOLL` を有効にして、システムコールの回数が 0 に近づくことを、`strace -c` で確認する。
- **eBPF**: Linux のみ。`bpftrace` で、システムコールの回数をプロセスごとに数える。例: `bpftrace -e 'tracepoint:syscalls:sys_enter_read { @[comm] = count(); }'`。(**このコマンドは、書き方の例で、この環境では実行していない。**)
