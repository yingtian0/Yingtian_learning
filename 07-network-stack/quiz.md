**5.** イーサネット 14 + IP 20 + UDP 8 + データ 21 = 63 バイト。ヘッダが 42 バイトで、データより大きい。小さいメッセージほど、ヘッダのオーバーヘッドの割合が大きい。

**7.** 最下位ビット(0x01): 1 ならマルチキャスト。次のビット(0x02): 1 ならローカル管理(製造元の割り当てではない)。`02:...` は、ローカル管理のユニキャストアドレス。

**9.** ブロードキャストで「この IP の MAC は?」と聞き、該当する機器が、ユニキャストで答える。キャッシュに記録する。LAN の外なら、デフォルトゲートウェイの MAC。

**13.** 全体の長さ 0x0031 = 49。TTL = 0x40 = 64。プロトコル = 0x11 = 17 (UDP)。フラグ = 0x4000 → DF が立っている。送信元 = 192.0.2.1、宛先 = 192.0.2.2。チェックサム = 0x9a72。

**14.** `/24`: 256 個、ホスト用は 254 個(ネットワークアドレスとブロードキャストを除く)。`/22`: 1,024 個、1,022 個。

**21.** チェックサムは、16 ビットの語の「和」なので、足す順序に依存しない。語を入れ替えても、和が変わらない。1 ビットの反転は、和を変える。

**22.** チェックサムは、語の和の補数。1つの語が変わったとき、旧い語を引いて、新しい語を足せば、和の変化が分かる(RFC 1624)。全体を足し直す必要がない。演習1では、TTL とプロトコルの語が 0x4011 → 0x3f11 に変わり、チェックサムが 0x9a72 → 0x9b72 に変わった(再計算と一致)。

**24.** ループバックは、チェックサムのオフロード(`TXCSUM`)を使い、チェックサムの計算を省くため。バグではないと考えられるが、実際のネットワークインターフェース(パケットの取得に権限が要る)では、この環境で確認していない。ICMP のチェックサムは一致したので、自作の実装は、実際のカーネルのパケットで通った。

**28.** 経路の途中に、MTU が小さい区間があり、大きなパケット(DF 付き)が捨てられる。本来は、ICMP「断片化が必要」が送信元に届くが、ファイアウォールが ICMP を全部ブロックすると、届かない。送信元は同じ大きさで再送し続け、大きな通信だけが止まる。対策: ICMP type 3 code 4 を通す、MSS クランピング。

**29.** 1,472 バイト(1,500 − 20 − 8)。これを超えると、IP が断片化するので。

**31.** `10.1.5.5` → `10.1.0.0/16`(最長一致。`10.0.0.0/8` と `0.0.0.0/0` にも一致するが、`/16` が最長)。`10.2.3.4` → `10.0.0.0/8`(`/16` には一致しない)。

**32.** naive: O(エントリ数)。エントリ数に比例。trie: O(32)(最大 32 回の参照)。ノードが増えると、キャッシュに載らず、少しずつ遅くなる。dir248: O(1)。代償は、2^24 個の表(64 MiB)と、/25 以上のプレフィックスに追加の仕組みが要ること。

**33.** 検索結果を使わなかったため、コンパイラが、メモリ読み出しを、消した(境界チェックだけが残った)。0.2 ns は、1 サイクル(約 0.3 ns)未満で、ランダムな 64 MiB の表の読み出しとして、不可能。

**34.** スループット。互いに独立な検索を連続して行うので、CPU が複数のメモリ読み出しを重ねて処理できる(MLP、第1回)。1回の検索の待ち時間(依存した読み出し)ではない。

**36.** 同じ接続のパケットを、同じ経路に流すため(順序を保つ)。別々の経路に流すと、経路ごとの遅延が違い、受信側で順序が入れ替わり、TCP が損失と誤解して、性能が落ちる。

**39.** 長さを先頭に付ける(長さつきのメッセージ)、区切り文字(改行など)で区切る。

**40.** 受信バッファが一杯になり、UDP は、以降のデータグラムを黙って捨てる(送信側に通知なし)。TCP は、受信側のウィンドウが 0 になり、送信側が止まる(データを捨てない)。

**41.** この Mac の `net.inet.udp.maxdgram` が 9,216 で、OS の設定による上限。1,472 バイト以下に抑える理由は、それを超えると IP が断片化し、1個の断片の損失で全体が失われるため。

**45.** パケットの大きさが 512 倍になっても、1秒に送れる個数は 14% しか減らない。コストは、パケット1個あたり(システムコール、IP/UDP の処理)にかかり、バイトにはほとんどかからない。第6回のシステムコールの固定のコスト(約 85〜250 ns)と、同じ構造。

**46.** 84 バイト × 8 = 672 ビット。100 Gbps ÷ 672 ビット ≒ 1 億 4,880 万 pps。1 ÷ 1.488 億 ≒ 6.7 ns。1回のシステムコールだけで約 85 ns なので、カーネルの汎用のスタックでは、1コアで処理できない。オフロード、カーネルバイパス、複数コアが必要。

**48.** 測れたこと: ICMP の組み立て、チェックサム、ループバックの往復時間。測れなかったこと: 実際のネットワークを通る往復時間、経路の MTU、ルーターでの TTL の減少、ARP。
