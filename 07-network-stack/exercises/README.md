# 第7回 演習

すべて Go(標準ライブラリのみ)。macOS(Apple Silicon)で動作を確認した。**この環境では、パケットの取得(`tcpdump`、raw ソケット)に管理者権限が要り、使えないため、パケットを自分で組み立てる形にした**。Linux での実行は未確認。

```bash
cd 07-network-stack/exercises
```

## 進め方

第1〜6回と同じ。実行前に予想を書き、実行して比べ、外れたら理由を調べる。各計測は3回以上行う。

**注意**

- **ex5 は、自分自身(127.0.0.1)にだけ ping する**。外部のホストに送る改造をする場合は、**自分の管理下にある機器、または、ping を許可された宛先**にのみ行う。
- ex2、ex4 は、大量のデータグラムを、ループバックで送る。他のネットワークには出ない。
- ex5 は、このマシンのインターフェースの名前と MTU を表示する。**結果を公開する場合は、インターフェースの名前などから、環境が推測できることに注意する**(アドレスと MAC は、表示しない)。

## 演習1: パケットのヘッダ

[ex1_packet_headers/](ex1_packet_headers/)

```bash
cd ex1_packet_headers && go run .
```

**課題**

1. 出力の16進ダンプを、**自分の手で読む**。IP ヘッダの各フィールド(バージョン、ヘッダ長、全体の長さ、識別子、フラグ、TTL、プロトコル、チェックサム、送信元、宛先)を、バイト位置から特定する。本文 §3.1 の読み解きと照合する。
2. チェックサムを、**手で計算**する(10 バイト程度の短いデータで)。16 ビットの語を足して、桁あふれを足し戻して、反転する。コードの結果と、一致するか。
3. **改造**: 別の `Packet`(別の TTL、別のデータ、奇数長のデータ)を作る。奇数長のデータで、チェックサムの計算(最後の1バイトを、上位に置いて、0 を補う)が、正しく動くことを確認する。
4. **改造**: TCP のヘッダ(20 バイト: 送信元ポート、宛先ポート、シーケンス番号、確認応答番号、データオフセットとフラグ、ウィンドウ、チェックサム、緊急ポインタ)を組み立てる。**SYN パケット**(SYN フラグだけを立てたもの)を作り、疑似ヘッダ込みのチェックサムを計算する。(TCP の詳細は第8回。)
5. **改造**: IPv6 のヘッダ(40 バイト固定)を組み立てる。IPv4 にあった、ヘッダチェックサムと、断片化のフィールドが、無いことを確認する。UDP のチェックサムは、IPv6 では**必須**で、疑似ヘッダが、IPv6 アドレスになる。
6. **改造**: **断片化**を実装する。1500 バイトのパケットを、MTU 576 の区間のために、断片に切り分ける。識別子、MF フラグ、オフセット(8 バイト単位)を、正しく設定し、**再構成**して、元に戻ることを確認する。
7. 発展: Wireshark などで取得した実際のパケットの16進ダンプ(**自分の管理下の通信**のもの)を、この演習のコードで解析し、チェックサムが一致することを確認する。

## 演習2: UDP と TCP

[ex2_udp_vs_tcp/](ex2_udp_vs_tcp/)

```bash
cd ex2_udp_vs_tcp && go run .
```

**課題**

1. 3つの部(境界、バッファあふれ、最大サイズ)の結果を、本文 §5.4 の表と比べる。
2. **B(バッファあふれ)で、受信したデータグラムの個数と、バッファの大きさの関係**を調べる。1個あたり、何バイトとして計上されているか(512 バイトのデータ + 管理用の領域)。データグラムの大きさ(128、512、1472)を変えると、1個あたりの管理用の領域は、変わるか。
3. **C(最大サイズ)の上限を調べる**。`sysctl net.inet.udp.maxdgram`(macOS)や、Linux の `net.core.wmem_max` との関係。(**システムの設定を変更しない**。確認だけ。)
4. **改造**: TCP で、**長さを先頭に付けた**メッセージのやりとりを実装する(4 バイトの長さ + データ)。3つのメッセージを、バラバラに送っても、受信側が、境界を復元できることを確認する。
5. **改造**: TCP の受信側が、読まないとき、送信側の `Write` が、いつブロックするかを測る(送信バッファ + 受信バッファの合計)。UDP との違いを確認する。(第6回のバックプレッシャー。)
6. **改造**: UDP で、**順序の入れ替わり、重複**が起きるかを確認する(ループバックでは、通常起きない)。起きない理由は何か。
7. 発展: UDP の上に、**簡単な信頼性**(番号、確認応答、再送)を実装する。パケットの損失を、わざと起こして(確率で捨てる)、正しく届くことを確認する。(第8回の準備。)

## 演習3: 最長一致

[ex3_lpm_routing/](ex3_lpm_routing/)

```bash
cd ex3_lpm_routing && go run .
```

**課題**

1. 3つの実装(naive、trie、dir248)の、エントリ数ごとの検索時間のグラフを作る。**naive が、エントリ数に比例して遅くなる**ことを確認する。
2. **正しさの確認**を、自分で強化する。(a)特別な宛先(0.0.0.0、255.255.255.255、各プレフィックスの境界の、前後のアドレス)、(b)`/32` のプレフィックス(ホストルート)を追加して、naive と trie が一致するか。dir248 は、/25 以上を扱えない。
3. **改造**: dir248 を、**/25〜/32 に対応させる**(DIR-24-8 の第2段)。上位 24 ビットの表の項目に、「第2段の表を引く」という印を付け、下位 8 ビットで、第2段の表(256 項目)を引く。メモリと、検索時間は、どう変わるか。
4. **改造**: **マルチビットのトライ木**(1度に 8 ビットずつ、256 分岐)を実装する。通常の2進のトライ木と、検索時間、ノード数、メモリを比べる。
5. **改造**: ルートの分布を、現実に近づける(/24 が約 60%、/16〜/23 が約 35%、それ以外が少数)。現在の分布(ランダム)との違いで、trie のノード数と検索時間は、どう変わるか。
6. **改造**: `net/netip` の `Prefix.Contains` を使った、**別の**ナイーブな実装と、照合する(実装を、できるだけ別にして、共通のバグを避ける)。
7. 発展: **ルートの追加と削除**(更新)の速度を測る。trie の削除で、不要になったノードを回収する。dir248 の更新(ルートを 1 つ追加するのに、最大 2^16 項目を書き換える)の、コストを測る。経路が頻繁に変わる環境で、どの実装が向くか。

## 演習4: UDP のコスト

[ex4_udp_overhead/](ex4_udp_overhead/)

```bash
cd ex4_udp_overhead && go run .
```

**課題**

1. データの大きさごとの、pps と MB/s の表を作り、**pps が、大きさによらず、ほぼ一定**であることを確認する。3回測って、ばらつきを見る。
2. **損失(1,024 B と 1,472 B)が、再現するか**確認する。再現するなら、受信側が追いつかない原因を調べる(受信バッファの大きさ、`GOMAXPROCS`)。
3. **改造**: 送信側を、複数の goroutine(1、2、4、8)にして、pps を測る。スケールするか。ソケット1つに、複数の goroutine が書くのと、ソケットを複数持つのとで、違いが出るか。
4. **改造**: 受信側を、別のプロセスにする(送信側と受信側が、同じ Go のスケジューラを共有しないようにする)。pps と損失は、どう変わるか。
5. **改造**: 送信に `WriteMsgUDP` や、第6回の `sendmmsg`(Linux)を使い、**複数のデータグラムを、1回のシステムコールで送る**。pps は、どれだけ上がるか。(第6回の、固定のコストを薄める話。)
6. **Linux で実行できるなら**: `perf` や `strace -c` で、システムコールの回数と、カーネル内の時間(ネットワークスタックの各部)を見る。
7. 発展: `GOMAXPROCS=1` と既定で比べる。

## 演習5: ping をゼロから

[ex5_ping/](ex5_ping/)

```bash
cd ex5_ping && go run .
```

**課題**

1. 最初の3回の応答の、IP と ICMP の各フィールド(TTL、プロトコル、type、code、シーケンス番号)を読む。**応答が 84 バイトである理由**を、IP ヘッダ(20)+ ICMP ヘッダ(8)+ データ(56)から説明する。
2. **ICMP のチェックサム検算が true になること**を確認する。これは、演習1と同じ関数が、**実際のカーネルのパケット**で通ることの、確認である。
3. **IP ヘッダのチェックサム欄が 0 で、検算が false になる**理由を調べる。`ifconfig lo0` の `options` を見て、チェックサムのオフロードと結びつける。**ループバックでは、なぜ計算が省略されるのか**。
4. **改造**: データのサイズを、56 バイトから、1000、1472、1473、9000、20000 に変えて、ping する。どこで、失敗するか(第7回の演習2の、最大サイズとの関係)。
5. **改造**: **ICMP のチェックサムを、わざと壊して**送る。応答は返るか。(カーネルが、チェックサムを検証して、捨てるか。)
6. **改造**: 往復時間の分布のヒストグラムを作る。最小(56.8 µs)と、中央値(89.7 µs)の差は、何によるか(割り込み、スケジューリング、キャッシュ)。第6回の、UDP のエコー(約 40 µs)や、第3回の、パイプでの往復と比べて、ICMP のほうが遅い理由は。
7. **自分の管理下にある、別の機器**(例えば、同じ LAN のルーターや、自分の別の PC)がある場合に限り、そこへ ping する。往復時間は、ループバックと、どれだけ違うか。
8. 発展: **traceroute** を実装する。TTL を 1、2、3… と増やして、UDP や ICMP を送り、「TTL 超過」の応答を受け取る。(**自分の管理下のネットワークで、控えめな頻度で**。この環境では、ループバックの TTL が減らないため、確認できない。)
