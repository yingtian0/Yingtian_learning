# 第9回 演習

すべて Go(標準ライブラリのみ)。5本は、1つのモジュール(`ex9web`)にまとめてあり、共通の道具を `internal/` に置いた。macOS(Apple Silicon)で動作を確認した。**Linux での実行は未確認**。

```bash
cd 09-tls-http-and-web/exercises
go run ./ex1_tls_handshake
go run ./ex2_http_versions        # 引数 1〜6 で、1 つのケースだけ実行できる
go run ./ex3_cert_chain
go run ./ex4_http_wire
go run ./ex5_cache_compress
```

| ディレクトリ | 内容 |
|---|---|
| `internal/pki` | 使い捨ての CA と証明書を、実行時に作る(ECDSA / RSA) |
| `internal/netsim` | ループバックの接続に、**片道の遅延**と、**1 回きりの停止**を加える(帯域の制限はない) |

## 進め方

第1〜8回と同じ。実行前に予想を書き、実行して比べ、外れたら理由を調べる。

**注意(安全のため)**

- **すべて、ループバック(127.0.0.1)だけ**を使う。外部のサイトには接続しない。外部の測定をする改造は、**自分の管理下にあるサーバー**にだけ行う。
- 鍵と証明書は、**演習のために作る、使い捨てのもの**。本物の認証局の信頼とは無関係。**これらの鍵や証明書を、本番の環境に、使わない**。
- **`InsecureSkipVerify = true` は、演習3で、危険性を示すためにだけ使っている**。自分のコードに、持ち込まない。
- ex4 の C は、**メモリ内の、簡易なパーサー**による、概念の説明で、**実在のサーバーを攻撃する道具ではない**。ループバックの、自分で起動したサーバーにだけ送る。

## 演習1: TLS のハンドシェイク

[ex1_tls_handshake/](ex1_tls_handshake/)

**課題**

1. A の、送受信の塊から、TLS 1.2 と 1.3 の、往復の数を確認する。**ClientHello の大きさ(241 B と 247 B)**が、ほぼ同じなのに、**サーバーの最初の応答が、1.3 のほうが大きい(1,307 B 対 1,156 B)**理由を考える(1.3 は、Finished まで、1 つの塊に入っている)。
2. B の、往復時間を加えた測定を、**3回以上**行って、ばらつきを見る。往復時間を 100 ms、20 ms に変えて(`oneWay` を変える)、**時間が、RTT に比例する**ことを確認する。
3. **改造**: 証明書の鎖の長さを変える(葉だけ、葉 + 中間 1 つ、中間 2 つ)。ハンドシェイクのバイト数と、検証の CPU は、どう変わるか。
4. **改造**: `tls.Config.CipherSuites`(TLS 1.2 のみ)を、AES-GCM と ChaCha20-Poly1305 で変えて、CPU を比べる(ただし、ハンドシェイクではなく、**データの暗号化**の速度として、測る方が適切)。
5. **改造**: **データの暗号化の速度**を測る。100 MB を、TLS 接続で送り、MB/s を測る。平文の TCP と比べる。
6. **改造**: **クライアント認証**(mTLS)を有効にする。サーバーが、クライアントの証明書を要求し、検証する。ハンドシェイクの、塊の数と、CPU は、どう変わるか。
7. **改造**: セッションチケットの鍵を、サーバー側で、変える(`SetSessionTicketKeys`)。古いチケットでの再開が、失敗することを確認する。
8. 発展: Go の `tls.Config.GetConfigForClient` で、SNI ごとに、別の証明書を返す、マルチテナントのサーバーを作る。
9. 発展: **0-RTT** を試せる実装(quic-go など)で、0-RTT の往復を測る。(外部の依存が要るので、この環境では扱っていない。)

## 演習2: HTTP のバージョン

[ex2_http_versions/](ex2_http_versions/)

**課題**

1. 6 つのケースの、結果を表にする。**HTTP/2 が、約 3 RTT で、60 個を取得する**ことを、数式で説明する。
2. **接続数が、実行ごとに、ばらつく**(6 本の上限で、8〜14 本)ことを、複数回で確認する。`MaxConnsPerHost` と、Go の標準ライブラリの動作(待っているリクエストのために、余分に接続を張る)との関係を調べる。
3. **改造**: リソースの大きさを、10 KB から 1 MB に変える。**帯域の制限がない**ので、結果は、どう変わるか。次に、`netsim` に**帯域の制限**(例: 10 Mbps)を加える改造をして、HTTP/1.1 の 6 本と HTTP/2 の差が、どう変わるかを見る。
4. **改造**: 往復時間を、10 ms、50 ms、200 ms と変える。**RTT が大きいほど、HTTP/2 の利点が、大きくなる**ことを確認する。
5. **改造**: 停止の位置(`At`)と長さ(`Dur`)を変える。**停止が早いほど(接続の初期)**、影響は、どう変わるか。
6. **改造**: 停止を、**複数回**(例えば 3 回)にする(`Stall` を、複数回発火するように拡張)。HTTP/2 と HTTP/1.1 の差は、どう変わるか。**損失が、頻繁なほど、HTTP/2 の優位は、縮むか、逆転するか**。
7. **改造**: HTTP/2 で、`SETTINGS_MAX_CONCURRENT_STREAMS` を、小さく(例えば 10)する(`http2.Server` の設定)。60 個を、同時に出した場合の、全体の時間は、どう変わるか。
8. 発展: **HTTP/3**(QUIC)を試す。quic-go などの実装を使い、停止の模擬(UDP のパケットを、一定時間遅延させる)で、他のストリームが、止まらないことを確認する。(外部の依存が要る。この環境では、扱っていない。)

## 演習3: 証明書の鎖

[ex3_cert_chain/](ex3_cert_chain/)

**課題**

1. 出力の、証明書の中身を読む。**有効期間、SAN、CA フラグ、鍵の用途**が、鎖の各段で、どう違うか。
2. 9 つの検証の結果を、**エラーメッセージの文面**から、原因を言い当てる練習をする(メッセージを隠して、原因だけを推測する)。
3. **改造**: **ワイルドカード**の証明書(`*.example.test`)を作る。`a.example.test` には有効で、`a.b.example.test` と `example.test` には無効であることを確認する。
4. **改造**: **名前の制約**(Name Constraints)を、中間 CA に付ける(`PermittedDNSDomains`)。その中間 CA が、範囲外のドメインの証明書を発行しても、検証が失敗することを確認する。
5. **改造**: 証明書の**失効**を模擬する。自作の失効リスト(シリアル番号の集合)を持ち、検証の後に、確認する。(Go の標準の `Verify` は、失効を確認しない。)
6. **改造**: **クロス署名**(同じ中間 CA を、別のルートも署名する)を作り、**クライアントの信頼するルートが違っても、検証が通る**ことを確認する。
7. **改造**: **有効期間の境界**を試す。`NotAfter` の 1 秒前、1 秒後で、`Verify` の結果が変わることを確認する。**時計がずれたクライアント**(数分遅れている)が、まだ有効でない証明書を、拒否する場面を考える。
8. 発展: **自分が管理する、実際のサーバー**(例えば、Let's Encrypt の証明書を使うもの)の証明書の鎖を、`openssl s_client -showcerts` で取得し、この演習のコードで、解析する。

## 演習4: HTTP の、実際のバイト

[ex4_http_wire/](ex4_http_wire/)

**課題**

1. A の、パイプライン(1 回の write で、2 つのリクエスト)が、**2 つのレスポンスとして、順に返る**ことを確認する。`Content-Length` と `chunked` の、**本体の区切り方**を、バイト単位で読む。
2. **改造**: A で、`Connection: close` を外して、**keep-alive** の接続で、リクエストを 3 回、順に送る。**応答の境界**を、`Content-Length` だけで、見つけるパーサーを書く。
3. **改造**: B で、**複数のストリーム**(ストリーム 1、3、5)に、HEADERS を送る。レスポンスが、**入り交じって**返る(順序が入れ替わる)ことがあるか。
4. **改造**: B で、HEADERS に、**Cookie などの、長いヘッダ**を足す。HPACK の動的な表で、**2 回目以降のリクエストが、小さくなる**ことを確認する(動的な表への登録は、`0x40` のリテラルで、手動で組み立てる必要がある。難しい。RFC 7541 の付録 C の例を、参考にする)。
5. **改造**: B で、**不正なフレーム**(例えば、ストリーム 0 の HEADERS)を送り、サーバーが、`GOAWAY` で接続を閉じることを確認する。
6. **改造**: C の簡易パーサーに、**もう 1 つの曖昧さ**(例えば、`Transfer-Encoding: xchunked` や、ヘッダ名の前後の空白)を加え、パーサーの違いで、解釈がずれることを確認する。**ずれを防ぐには、パーサーをどう作るべきか**を、考える。
7. **改造**: C の最後の部分(実際の Go のサーバー)で、**`Content-Length` が 2 つ、異なる値で、書かれたメッセージ**を送る。Go のサーバーは、どう扱うか。
8. 発展: 前段のプロキシ(`httputil.ReverseProxy`)と、後段のサーバーを、自分で起動して、**前段が、どちらの長さを使うか**を、確認する。**(自分で起動した、ループバックのものだけで)**

## 演習5: キャッシュと圧縮

[ex5_cache_compress/](ex5_cache_compress/)

**課題**

1. A の、3つのリクエストの、ネットワークのバイト数を、確認する。**304 の 117 バイトの内訳**(ステータス行、ヘッダ)を、考える。
2. **改造**: `Cache-Control: max-age=60` を付けて、クライアントが、**2 回目に、リクエストを送らない**(キャッシュを使う)ようにする。Go の `http.Client` には、標準のキャッシュがないので、簡単なキャッシュを自作する。
3. **改造**: `Last-Modified` と `If-Modified-Since` で、同じ動作を実装する。ETag との違いは。
4. **改造**: B に、**実際のテキスト**(例えば、自分の PC にある、README やソースコードを連結したもの)を加える。**人工のデータ(0.3%)と比べて**、圧縮率は、どれくらいか。
5. **改造**: **Brotli や zstd**(外部のライブラリが要る)を、gzip と比べる。**圧縮率と速度**の、トレードオフを見る。
6. **改造**: **圧縮の辞書**(zstd の辞書、または Go の `compress/flate` の `NewWriterDict`)で、**小さな JSON**(1 KB)の圧縮率が、どれだけ改善するか。(小さいデータほど、辞書の効果が大きい。)
7. 発展: **CRIME/BREACH の原理を、実験で確認する**。秘密の文字列を含むレスポンスを、圧縮してから、**長さだけ**を観察する。推測した文字列を混ぜると、長さが変わることを確認する。(**自分の、ローカルのコードの中だけで。**)

## 参考結果(Apple M5、macOS、論理 CPU 10、Go 1.26.5)

| 演習 | 結果 |
|---|---|
| 1 | 往復: TLS 1.2 = 2、1.3 = 1。RTT 50 ms で、1.2 = 106.4 ms、1.3 = 54.4 ms。CPU: ECDSA 0.35 ms、RSA 3072 = 2.05 ms、再開 0.21 ms。バイト数: ECDSA 1,615 B、RSA 2048 = 2,593 B |

| 4 | HTTP/2 のヘッダブロック 14 B(HTTP/1.1 は 35 B)。`0x88` = `:status 200`。Go のサーバーは、CL と TE の両方があると、TE を優先し、2 つのリクエストを処理 |
