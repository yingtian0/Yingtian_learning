**1.** 並行は、複数の仕事が同時進行している状態を作る(構造)。並列は、実際に同時に実行する(実行)。コアが1つでも、OS のプリエンプション(第3回)が、任意の位置に切り替えを差し込むので、競合は起きる。

**3.** データ競合は、順序づけのない同時アクセス(少なくとも片方が書き込み)で、機械的に判定できる。競合状態は、タイミングで結果の正しさが変わること。例(データ競合なし、競合状態あり): 各メソッドをロックで守ったうえで、「残高を調べて、足りれば引き出す」を2つのロック区間に分けたコード。

**4.** データ競合ではない(各アクセスは、ロックで順序づけられている)ため。バグと言える根拠は、不変条件(残高がマイナスにならない)が破れること。

**6.** `-race` 付きの実行は遅く、確認と引き出しの間の隙間が広がり、割り込まれやすい。まれなバグは、実行を遅くしたり、意図的に待ちを入れたり、多数回、繰り返したりして、見つけやすくできる。

**8.** 保証するのは、その1回の操作が分割されないこと。他のメモリ操作との順序は別の話で、C/C++ では、memory_order で指定する。

**9.** TAS は、待つ間も `exchange`(書き込み)を繰り返し、そのたびにキャッシュラインが待ち手の間を往復する。TTAS は、待つ間は読むだけで、ラインは共有状態のまま動かない。放されたときだけ無効化される。

**10.** 番号順に FIFO で処理するので公平。ただし、次の番号のスレッドが OS に止められている(論理 CPU より多いスレッドで起きやすい)と、その後ろの全員が、空回りしながら待たされる。

**14.** 分かっていること: 結果は正しく、アトミック加算のほうが遅かった(約 0.34〜0.41 秒対 0.20〜0.22 秒)。分かっていないこと: 理由。mutex では、ロックを放したスレッドがすぐ取り直せるので、キャッシュラインの往復が減る、という仮説があるが、未検証。

**17.** 読み手 R1 が読み取りロックを持つ。書き手 W が `Lock` を呼び、待つ(新しい読み手は止められる)。R1 が、再度 `RLock` を呼ぶと、W を待って止まる。W は R1 の解放を待つ。デッドロック。

**19.** ロックに全体で一意な順序(例えば、口座 ID の昇順)をつけ、常に小さいほうから取る。振替の場合は、`from` と `to` の ID を比べ、小さい口座のロックを先に取る。

**20.** `abba` は、すべての goroutine が眠っているため、ランタイムが検出する。`hidden` は、他の goroutine が、周期的に眠っては起きている(タイマーを持つ)ので、「全員が眠っている」と判断されない。実務では、タイムアウト、goroutine のダンプ(pprof、SIGQUIT)、ヘルスチェックで見つける。

**23.** ロックを使う方式: ロックを持ったスレッドが止まれば全員が止まる。ロックフリー: どのスレッドが止まっても、システム全体では、誰かが進む。ウェイトフリー: どのスレッドも、有限の手数で終わる。CAS のやり直しループは、ロックフリー。

**25.** あるスレッドが参照を持っている間、GC はそのメモリを再利用しない。そのため、同じアドレスが別物として戻ってくることがない。`sync.Pool` などで、自分でノードを再利用すると、戻ってくる。

**27.** 競合が激しいと、CAS が失敗してやり直すことが増え、捨てられる仕事が増える(未検証)。ロックフリーを選ぶ正当な理由は、ロックを持ったスレッドの停止で、全体が止まるのを避けたいとき(シグナルハンドラの中、リアルタイム性が必要な場面など)。

**33.** USL の κ の項(N の 2 乗に比例する、一貫性のコスト)が、N が大きくなると支配的になり、処理量が減り始める。共有カウンタのキャッシュラインが、コア間を往復するコストが、スレッドが増えるほど重くなる。

**34.** (1)共有をなくす(スレッドごとのカウンタ + 集計)、(2)ロックを分割する、(3)ロックの保持時間を短くする、(4)アトミック操作に置き換える。

**36.** コンセンサス数が、CAS は無限、test-and-set は 2。3 つ以上のスレッドが合意できる(どんなウェイトフリーのオブジェクトも作れる)のは CAS。
