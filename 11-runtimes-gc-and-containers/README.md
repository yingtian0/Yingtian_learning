## 2. GC の基本

### 2.1 GC が、解くべき問題

プログラムは、メモリを確保する(`new`、`make`)。**いつ、そのメモリが、不要になったか**は、プログラムを、実行しないと分からない。手動で `free` すると、次の 2 つの間違いが、起きうる(第2回)。

- 解放し忘れる(リーク)。
- 解放した後に、使う(use-after-free。セキュリティ上の脆弱性の、大きな原因)。

GC は、これを、ランタイムが、自動で判定する仕組みである。**判定の基準**を、先に決める。

> **到達可能性**: 「根(スタック上の変数、グローバル変数、レジスタ)から、ポインタをたどって、到達できるオブジェクト」は、使われうる(生きている)。到達できないものは、二度と使えないので、ゴミ。

これは、**近似**である。到達できても、プログラムが、二度と使わないオブジェクトは、ある(生きていると判定されて、残る)。逆に、使われるのに、到達できない、ということはない(正しさは、守られる)。

### 2.2 参照カウント

各オブジェクトが、「自分を指す、ポインタの数」を持つ。0 になったら、すぐ解放する。

- 利点: **すぐ解放**される(停止がない、メモリの使用量が読みやすい)。
- 欠点 1: **循環したゴミが、解放できない**。A が B を指し、B が A を指すと、どちらも、カウントが 1 のまま。
- 欠点 2: ポインタを書き換えるたびに、カウントの更新が要る。マルチスレッドでは、**アトミック操作**(第4回)で、遅い。

CPython、Swift、Rust の `Rc` / `Arc` は、参照カウントを使う。循環は、別のサイクル検出の GC や、弱い参照で、扱う。

**演習3 C**: 5 個のオブジェクトの塊を、2 万個作った。半分は木(非循環)、半分は輪(循環)。すべてをゴミにしたとき、解放できたのは、**10 万個のうち 5 万個**。**循環した 5 万個(50.0%)が、漏れた**。

### 2.3 トレース GC: マーク & スイープ

根から、ポインタをたどって、到達できるものに、印(マーク)を付ける。その後、ヒープ全体を走査して(スイープ)、印のないものを、空きにする。

- 利点: 循環を、自然に扱う。ポインタの更新に、コストがない(書き込みバリアが要る場合を除く、§3)。
- 欠点 1: **仕事量が、生きている量と、ヒープ全体の、両方に比例する**(マークは、生きている量。スイープは、ヒープ全体)。
- 欠点 2: オブジェクトは、動かない。**空きが、散らばる(断片化)**。

### 2.4 トレース GC: コピー(半空間)

ヒープを、2 つに分ける。使っている半分から、生きているものだけを、もう半分へ、コピーする。コピーが終わったら、元の半分は、丸ごと空き。

- 利点: **生きているものだけ**を触る。コピー先で、**詰まる**(断片化しない)。確保は、「ポインタを進めるだけ」で、速い。
- 欠点: **半分の領域が、常に空いている**(メモリを 2 倍、使う)。オブジェクトが、動くので、**そのアドレスを、指している全ポインタを、書き換える**必要がある。

### 2.5 実測: 演習3 A・B

おもちゃのヒープ(200 万個のオブジェクト、各 2 つの参照)で、2 つの方式の仕事量と、時間を測った(5 回の中央値)。

| 生きている割合(実際) | マーク & スイープ: 触った数 / 時間 | コピー: コピーした数 / 時間 |
|---|---|---|
| 3.0% | 2,059,050 / 4.4 ms | 59,050 / 1.6 ms |
| 14.8% | 2,296,135 / 12.2 ms | 296,135 / 3.6 ms |
| 29.5% | 2,590,310 / 22.2 ms | 590,310 / 6.2 ms |
| 53.4% | 3,067,067 / 39.0 ms | 1,067,067 / 11.1 ms |

読み取れること(この実験の範囲で):

- マーク & スイープの「触った数」には、**ヒープ全体(200 万)の走査が、常に乗る**。コピーは、生きているものだけ。
- 時間も、コピーのほうが、約 2.7〜3.5 倍、短かった。**ただし**、コピーは、**半分の空き領域**が要る(メモリは 2 倍)。また、このおもちゃは、ポインタ先のキャッシュミスが支配的で(第1回)、実際のランタイムの、数値ではない。
- 注意: 「割り当て時の割合」を 5〜90% で指定したが、**実際に到達可能だったのは、その約 6 割**だった(おもちゃのヒープの作り方で、一部が、つながらなかった)。表は、実際の割合で読む。

**断片化(演習3 B)**: 100 万個のヒープで、マーク & スイープの後、空きは **703,180 個**あるが、散らばっていて、**最大の連続した空きは、31 個**だった。1,000 個ぶんの連続した領域が欲しくても、確保できない(第2回の、外部断片化と、同じ問題)。コピーの後は、生きているもの 296,820 個が、先頭に詰まり、**残りの 703,180 個が、1 つの連続した空き**になる。

### 2.6 世代別 GC

**弱い世代仮説**: 「大半のオブジェクトは、若くして死ぬ」。この経験則を使う。ヒープを、**若い世代**と**老いた世代**に分ける。若い世代だけを、頻繁に集める(生き残ったものを、老いた世代へ移す)。老いた世代は、たまにしか集めない。

- 利点: 若い世代の GC は、生きているものが少ないので、安い(コピーする量が少ない)。
- 代償: 老いた世代のオブジェクトが、若いオブジェクトを指すとき、若い世代の GC は、その参照も、根として扱う必要がある。そのため、**老いた世代への書き込みを記録する仕組み**(書き込みバリア、カードテーブル)が要る。

**演習3 D(モデル)**: 200 万回の割り当て。95% は、平均 50 回の割り当ての間だけ生き、5% は、ずっと生きる、という分布。

| 方式 | コピーしたオブジェクト数 | 割り当て 1 回あたり |
|---|---|---|
| 世代別でない(全体をコピー) | 1,978,765 | 0.989 |
| 世代別(若い世代 5,000 個) | 227,817 | 0.114 |
| 世代別(若い世代 20,000 個) | 251,005 | 0.126 |
| 世代別(若い世代 100,000 個) | 206,219 | 0.103 |

世代別のほうが、コピーが、約 **8〜10 分の 1** だった。**これは、「95% が、すぐ死ぬ」と、モデルに仮定した結果**である。実際のプログラムが、この分布に従うかは、別の問題(§9 の論点 2)。このモデルは、書き込みバリアの、コストを含まない。

## 3. 並行 GC と書き込みバリア

### 3.1 なぜ並行が必要か

マークを、アプリを止めて(stop-the-world、STW)行うと、**ヒープが大きいほど、停止が長い**。演習2 A で測ると、ポインタだらけのヒープの、マークの時間は、100 MB で約 7 ms、400 MB で約 28 ms、800 MB で約 58 ms だった(§4.4)。数十 ms の停止は、第15回で見る、遅延の目標(p99 が、数十 ms)に、収まらない。

そこで、**アプリ(ミューテータ)が走っている間に、GC が、並行にマークする**。

### 3.2 並行マークの問題: ミューテータが、グラフを書き換える

GC が、グラフをたどっている最中に、ミューテータが、ポインタを書き換えると、**生きているオブジェクトを、見落とす**ことがある。これを、3 色で説明する。

| 色 | 意味 |
|---|---|
| 白 | まだ見ていない(最終的に、白のまま残ったものが、ゴミ) |
| 灰 | 見つけたが、そこから出る参照を、まだたどっていない |
| 黒 | 見つけて、出る参照も、すべてたどった |

**見落としが起きる条件**(両方が、同時に成り立つとき):

1. 黒のオブジェクトが、白のオブジェクトへの参照を、新しく持つ。
2. その白のオブジェクトへ至る、灰からの経路が、すべて、断たれる。

黒は、もう、たどらない。灰からの経路は、無い。白は、誰にも見つけられず、**生きているのに、ゴミと判定され、解放される**(メモリ破壊)。

### 3.3 書き込みバリア

ポインタの書き込みの直前(または直後)に、**ランタイムが挿入した、小さなコードを実行する**。これが、書き込みバリアである。条件 1 か 2 の、どちらかを、起きないようにする。

- 挿入型(Dijkstra): 「黒が、白を指す」ときに、その白を、灰にする(条件 1 を防ぐ)。
- 削除型(Yuasa): 「参照を消す」ときに、消される先を、灰にする(条件 2 を防ぐ)。

Go は、この 2 つを組み合わせた、**ハイブリッド書き込みバリア**を使う(Go 1.8 以降。詳細は Go のドキュメントと、提案文書を参照。ここでは、概念だけを示す)。**代償**: GC が動いている間、ポインタの書き込みが、遅くなる(バリアの分)。GC が動いていないときは、バリアは、切られている(フラグの確認だけ)。

### 3.4 ミューテータ・アシスト

アプリが、GC より速く、割り当てると、GC が、追いつかない(ヒープが、目標を超える)。そこで、**割り当てを多くする goroutine に、GC の仕事の一部を、手伝わせる**(アシスト)。割り当てが、**遅くなる**。これは、アプリへの、GC の「課税」である。

## 4. Go の GC

### 4.1 設計の選択

| 選択 | Go | 理由(Go チームの公開された説明による) | 代償 |
|---|---|---|---|
| 並行か | **並行**(STW は、非常に短い) | 遅延の目標 | CPU の一部を、GC に取られる。書き込みバリアのコスト |
| 世代別か | **いいえ** | 設計の単純さ。書き込みバリアのコストを避ける。Go は、値型とスタック割り当てが多く、若いオブジェクトの寿命の分布が、他の言語と違う、という議論がある | 若いゴミを、効率よく集められない(§2.6) |
| 動かすか(コンパクション) | **いいえ**(非移動) | ポインタを、C と共有できる(cgo)。ポインタの書き換えが不要 | 断片化。アロケータが、サイズクラスで、対処(第2回) |

注意: 世代別の GC が、Go で有利になるかは、研究の対象で、**公開された実験的な取り組みがある**(最新の状況は、Go のリリースノートで確認すること)。この講義は、現時点の主流の実装を、説明する。

### 4.2 サイクルの流れと、`GOGC`

1 回の GC サイクルは、おおよそ、次のとおり。

1. **スイープの終了**(前回の残り)。
2. **STW(短い)**: 書き込みバリアを有効にし、根を集める。
3. **並行マーク**: GC のワーカーが、並行にマークする。アシストも動く。
4. **STW(短い)**: マークの終了を確認する。
5. **並行スイープ**: ゴミのメモリを、アロケータに戻す(割り当てのときに、遅延して行われる)。

**いつ、次の GC を始めるか**は、`GOGC` で決まる。

> ヒープの目標 ≈ 前回の GC 後の、生きているヒープ × (1 + GOGC / 100)

`GOGC=100`(既定)なら、生きている量の 2 倍まで、ヒープが膨らんだら、次の GC を始める。これは、**メモリと CPU の、交換レート**である。

- `GOGC` を上げる → GC の回数が減る(CPU が減る)。ヒープが大きい(メモリが増える)。
- `GOGC` を下げる → 逆。

### 4.3 実測: 演習1(GC のコスト)

条件: 子プロセス、`GOMAXPROCS=2`(GC が、アプリと、CPU を奪い合う)。ポインタを含む、64 バイトのノードの連結を、生きているヒープとして持ち、2 秒間、4 KB の「すぐ捨てるデータ」を、割り当て続ける。

**A. 生きているヒープ = 100 MB で、`GOGC` を変える**

| GOGC | GC 回数/秒 | GC の CPU 割合 | ヒープの最大 | 理論値(100 MB × (1+GOGC/100)) | 割り当て速度 GB/秒 | 最大停止 |
|---|---|---|---|---|---|---|
| 25 | 76.4 | 72.0% | 160 MB | 125 MB | 2.46 | 192 µs |
| 50 | 76.0 | 71.0% | 199 MB | 150 MB | 5.29 | 32 µs |
| 100 | 54.5 | 51.7% | 322 MB | 200 MB | 9.20 | 34 µs |
| 200 | 25.0 | 24.9% | 833 MB | 300 MB | 14.13 | 41 µs |
| 400 | 12.0 | 13.4% | 2270 MB | 500 MB | 14.64 | 69 µs |

**B. `GOGC=100` で、生きているヒープを変える**

| 生きている量 | GC 回数/秒 | GC の CPU 割合 | ヒープの最大 | 理論値 | 割り当て GB/秒 |
|---|---|---|---|---|---|
| 25 MB | 218.5 | 50.1% | 82 MB | 50 MB | 9.24 |
| 100 MB | 54.0 | 51.6% | 379 MB | 200 MB | 9.15 |
| 400 MB | 13.5 | 50.6% | 1305 MB | 800 MB | 9.18 |

読み取れること:

1. **`GOGC` は、CPU とメモリの交換レート**。`GOGC` を 25 → 400 にすると、GC の CPU 割合は 72% → 13% に下がり、割り当て速度(アプリが進んだ量)は 2.46 → 14.64 GB/秒に上がった。代償は、ヒープの最大が 160 MB → 2270 MB。
2. **B の、GC の CPU 割合は、生きている量によらず、約 50% で、ほぼ一定**。生きている量が 4 倍になると、1 回の GC は、約 4 倍重いが、GC の頻度は、約 4 分の 1。**割り当て速度が、同じなら、GC の CPU 割合は、`GOGC` だけで、決まる**、という、理論的な見通し(GC のコスト ∝ 生きている量、頻度 ∝ 割り当て速度 ÷ 生きている量)と、一致している。
3. **ヒープの最大は、理論値を、上回った**(例: `GOGC=100`、100 MB で、322〜379 MB。理論値 200 MB)。**理由の仮説**: GC のマークの最中も、アプリは、9 GB/秒で割り当て続けており、**目標に達してから、マークが終わるまでの間に、さらにヒープが増える**。`GOGC` を上げるほど、1 回の GC の間に、増える量が大きい(2270 MB 対 理論値 500 MB)。**これは、仮説であり、別の実験で確かめていない**(§10)。
4. **最大停止は、すべて、数十〜百数十 µs**(`GOGC=25` の 192 µs は、1 回だけの外れ値の可能性が高いが、確かめていない)。停止だけを見ると、GC は、ほとんど無視できる。**だが、次を見る**。

### 4.4 実測: 演習2(GC と、遅延の裾)

**A. 1 回の GC にかかる時間と、STW(`GOMAXPROCS=4`、5 回の中央値)**。GC のチューニングを切り、`runtime.GC()` を手動で呼んで、測った。

| 生きているヒープ | GC 1 回の時間 | 最大の STW 停止 |
|---|---|---|
| ポインタなし(`[]byte`)400 MB | 0.11 ms | 21 µs |
| ポインタだらけ 100 MB | 6.99 ms | 23 µs |
| ポインタだらけ 400 MB | 28.15 ms | 28 µs |
| ポインタだらけ 800 MB | 57.87 ms | 36 µs |

1. **ポインタを含まないデータは、GC が、中身を見ない**。400 MB でも 0.11 ms(中身を走査しない。大きさだけを記録している)。ポインタだらけの 400 MB の、**約 250 分の 1**。
2. ポインタだらけのヒープでは、GC の時間は、**生きている量に、ほぼ比例**した(約 0.07 ms/MB)。
3. **STW の停止は、ヒープの大きさに、ほとんど、依存しない**(21〜36 µs)。STW は、根を集めるときと、マークの終了の確認だけで、ヒープ全体を、たどらないため。

**B. GC が動き続けている間の、アプリの遅延**(3 秒。裏の 2 つの goroutine が、64 KB を、割り当て続ける。`GOMAXPROCS=4`)

| 生きているヒープ | GC 回数 | 1 ms タイマーのずれ p50 / p99 / 最大 | 1 回の処理の遅延 p50 / p99 / 最大 |
|---|---|---|---|
| ポインタなし 400 MB | 603 | 14 / 34 / 1496 µs | 1 / 14 / 261 µs |
| ポインタだらけ 400 MB | 80 | 18 / **20182** / 24062 µs | 1 / 18 / **16860** µs |

読み取れること(事実):

- ポインタなしでは、**GC が 603 回走っても**、タイマーのずれの p99 は、34 µs で、ほぼ無視できる。
- ポインタだらけでは、GC の回数は、80 回と、少ないのに、**タイマーのずれの p99 が、約 20 ms** になった。1 回の処理の遅延の最大も、約 17 ms だった。
- A で見たとおり、**STW の停止は、数十 µs**。したがって、**この 20 ms の遅延は、STW が原因では、ない**。

**原因は、確定できていない**。追加で、`GOMAXPROCS` を 2、4、8、10 に変えて、同じ実験を繰り返したところ、ポインタだらけの場合の p99 は、**どの設定でも、約 12〜34 ms で、残った**。処理の最大遅延は、`GOMAXPROCS=2` で、最大 29 ms まで悪化した。

**仮説(未検証)**: 1 回の GC のマークは、ポインタだらけの 400 MB で、約 28 ms かかる(A)。その間、全ての P(プロセッサ)が、GC のワーカー、アシスト、割り当てをする goroutine で、ふさがる。**タイマーを待つ goroutine を、実行する P が、空くまで、待たされる**。GC の間、**スケジューリングの遅延**が、マークの時間のオーダーで発生する、という説明。これなら、マークの時間(約 28 ms)と、遅延の大きさ(約 20 ms)が、同じオーダーであることと、矛盾しない。

確かめるには、`GODEBUG=gctrace=1` や、`runtime/trace` で、タイマーの goroutine が、どれだけ「実行可能だが、実行されていない」かを、直接見る必要がある。**この講義では、そこまでしていない**。

> **この実験が示す、確かなこと**: 「STW が短い」ことは、「GC が、遅延に影響しない」ことを、意味しない。**ポインタだらけのヒープでは、並行 GC でも、遅延の裾(p99)が、悪化しうる**。

## 5. チューニング

GC のコストは、**生きているヒープの大きさ**と、**ポインタの数**と、**割り当ての速度**で決まる(§4.3、§4.4)。チューニングは、この 3 つを減らす方向。

### 5.1 割り当てを減らす(1): エスケープ解析

Go のコンパイラは、変数が、関数の外に「逃げる」(エスケープする)かを、静的に調べる。逃げなければ、**スタックに置く**。スタックは、関数の終了で、自動的に解放され、GC は、関係しない。

```bash
go build -gcflags='-m' ./...     # エスケープの判定を表示
```

典型的に、ヒープに逃げる場合: ポインタを返す、インターフェースに入れる、クロージャに捕まる、大きさが、コンパイル時に分からないスライス。**見積もりではなく、`-gcflags=-m` で、確かめる**。

### 5.2 割り当てを減らす(2): `sync.Pool` と、再利用

一時的なバッファを、使い回す。`sync.Pool` は、GC のたびに、中身が、(段階的に)捨てられうる、**キャッシュ**である。「必ず残る」資源のプールには、使えない。

### 5.3 ポインタを減らす: データの配置

- `[]*T` より、`[]T`(値のスライス)。ポインタをたどる必要がなく、キャッシュにも優しい(第1回)。
- ポインタを含まない構造体の、大きな配列は、GC が、**中身を見ない**(演習2 A: 400 MB で、0.11 ms)。
- 大量のキーと値を、保持するときは、**ポインタを含まない、1 つの大きなバイト列に、詰める**設計がある(巨大なキャッシュ、時系列データ)。デバッグが難しくなる、**代償**がある。

### 5.4 `GOMEMLIMIT`(Go 1.19 以降)

`GOGC` は、「生きている量の、何倍まで」という、**相対的**な目標。しかし、コンテナのメモリ上限(§6.3)は、**絶対的**(例: 256 MiB)。そこで、**絶対的な目標**を、ランタイムに伝える。

- `GOMEMLIMIT=256MiB`: ランタイムが、ヒープ、スタック、ランタイム自身の使用量の、合計を、この値に近づけるよう、GC を、頻繁にする。
- `GOGC=off` と組み合わせると、「上限に近づくまで、GC をしない」。上限に近づくと、GC が、頻繁に走る。
- **ソフトな目標**であって、保証ではない。生きている量が、上限を超えれば、守れない。
- GC の CPU 時間が、全体の約 50% を超えないよう、ランタイムは、GC の CPU 使用を制限する(CPU リミッタ)。これがないと、上限に張り付いたまま、アプリが、ほとんど進まなくなる(死のスパイラル)。

**演習4**(生きているヒープ 100 MB、`GOMAXPROCS=2`、各 2 秒):

| 設定 | GC 回数/秒 | GC の CPU 割合 | ヒープの最大 | OS から得た最大 | 割り当て GB/秒 |
|---|---|---|---|---|---|
| `GOGC=100`(既定) | 53.0 | 52.3% | 322 MB | 340 MB | 8.89 |
| `GOGC=off`、上限 400 MiB | 49.5 | 46.2% | 372 MB | 390 MB | 10.45 |
| `GOGC=off`、上限 250 MiB | 69.5 | 64.1% | 229 MB | 244 MB | 6.58 |
| `GOGC=off`、上限 150 MiB | 79.0 | 73.2% | 135 MB | 147 MB | 1.40 |
| `GOGC=off`、上限 110 MiB | 76.9 | 70.3% | 138 MB | 149 MB | 1.00 |
| `GOGC=off`、上限 80 MiB(生きている量より小さい) | 75.4 | 70.9% | 138 MB | 150 MB | 0.95 |
| `GOGC=100` + 上限 150 MiB | 79.5 | 73.2% | 136 MB | 148 MB | 1.41 |

読み取れること:

1. **上限が、余裕を持っていれば(400 MiB)**、上限は、効かず、`GOGC=100` と、同じ挙動(約 50 回/秒、約 9〜10 GB/秒)。
2. **上限を締めるほど、ヒープは、上限に近づき、GC は増え、アプリの進みは、遅くなる**。上限 150 MiB では、割り当て速度が、約 9 GB/秒から **1.4 GB/秒**へ、**約 6 分の 1** に落ちた。**メモリを、CPU(= アプリの進み)と、交換した**。
3. **上限が、生きている量(100 MB)より小さい 80 MiB では、守れなかった**(ヒープは 138 MB まで)。アプリは、止まらず、進み続けた(0.95 GB/秒)。これは、**ソフトな上限**であり、**OOM を防ぐ保証ではない**ことを、示している。上限 110 MiB と、80 MiB で、ほぼ同じ挙動になったのは、生きている量が、どちらの上限よりも、大きいため(100 MB のデータ + ランタイムの管理分)、と考えられる。
4. **GC の CPU 割合が、70% を超えた**。ランタイムの、CPU リミッタは「約 50%」を、目標とする、と説明される。**測定値が、これを超えたのは、私が使った指標**(`/cpu/classes/gc/total:cpu-seconds`)が、**アイドルな P が、GC をした時間も、含む**ためかもしれないが、**確かめていない**。リミッタの実際の効き方は、この実験では、確認できていない。

**運用上の推奨**(これは、事実ではなく、推奨): コンテナのメモリ上限の **90% 前後**に `GOMEMLIMIT` を設定する。理由: ヒープ以外の使用量(スタック、cgo、ランタイム)が、ヒープの外にあるため。ただし、**数値は、アプリごとに、測って決める**。

### 5.5 観測

```bash
GODEBUG=gctrace=1 ./app 2>&1 | head   # GC のたびに、1 行(ヒープの大きさ、CPU 時間、停止)
```

```go
import "runtime/metrics"    // 演習1 で使った、安定した名前の指標
// /gc/cycles/total:gc-cycles、/cpu/classes/gc/total:cpu-seconds、/memory/classes/heap/objects:bytes
```

`pprof` の `heap`(何が、生きているか)と `allocs`(何が、割り当てられたか)の、区別も重要。**GC を速くするより、割り当てを減らすほうが、効く**ことが多い。

## 6. コンテナ

### 6.1 コンテナとは何か

コンテナは、**特別なカーネルの機能ではない**。**普通の Linux プロセス**に、次の 3 つの、既存のカーネルの機能を、組み合わせて、**隔離**と**制限**を、かけたもの。

| 機能 | 何をするか | 分類 |
|---|---|---|
| **名前空間(namespace)** | プロセスから**見える**ものを、分ける | 隔離(見えない) |
| **cgroup** | プロセスが**使える**資源の量を、制限する | 制限(使えない) |
| **ファイルシステムの層**(overlayfs など) | イメージを、層として重ね、コンテナごとに書き込みを分ける | 配布と、コピーオンライト |

加えて、**ケーパビリティ**(root の権限を、細分化)、**seccomp**(使えるシステムコールを、制限)が、攻撃面を減らす。

### 6.2 名前空間

| 名前空間 | 分けるもの | コンテナの中の、見え方 |
|---|---|---|
| PID | プロセス番号 | 最初のプロセスが PID 1。ホストのプロセスは、見えない |
| NET | ネットワークデバイス、ルーティング、ポート | 自分専用の、ネットワークインターフェース(§8) |
| MNT | マウントの木 | 自分専用の、ルートファイルシステム |
| UTS | ホスト名 | 自分専用のホスト名 |
| IPC | System V IPC、メッセージキュー | |
| USER | ユーザ ID の対応 | コンテナ内の root が、ホストでは、一般ユーザ |
| CGROUP | cgroup の、見える範囲 | |
| TIME | 時計のオフセット | |

**重要な点**: 名前空間は、**カーネルを共有したまま、見える範囲を変える**。同じカーネルが、全コンテナの、システムコールを処理する。**カーネルの脆弱性は、コンテナの隔離を、破りうる**(仮想マシンとの、大きな違い、§6.5)。

`linux_only/ns_demo.c` は、`clone` で、名前空間を作る例(この Mac では、**実行していない**)。

### 6.3 cgroup v2

cgroup は、プロセスを、階層的な**グループ**にまとめ、資源を、**制限**・**計測**する。

| ファイル | 内容 |
|---|---|
| `cpu.max` | `200000 100000` = 周期 100 ms あたり、200 ms の CPU 時間(= 2 CPU) |
| `cpu.weight` | CPU が取り合いのときの、相対的な重み(上限ではなく、**比率**) |
| `memory.max` | メモリの、**ハードな上限**。超えようとして、回収できないと、**OOM キラー**が、グループ内のプロセスを、強制終了 |
| `memory.high` | ソフトな上限。超えると、**回収が強まり、遅くなる**(殺さない) |
| `pids.max` | プロセス(スレッド)の数の上限(フォーク爆弾への対策) |
| `io.max` | ブロックデバイスの、帯域と IOPS の上限 |

**メモリ上限と、OOM**: コンテナが、`memory.max` を超えると、カーネルは、まず、ページキャッシュなどを回収する。それでも足りなければ、グループ内のプロセスを `SIGKILL` する。**終了コードは 137**(128 + 9)。**メモリは、CPU と違い、「待たせれば、解決」しない**ため、上限は、ハードである。Go のランタイムが、`GOMEMLIMIT`(§5.4)を、必要とする、根本の理由。

`linux_only/cgroup_probe.go` は、自分の cgroup の、`cpu.max`、`memory.max`、`cpu.stat` を、読む(**未実行**)。

### 6.4 overlayfs とイメージ

イメージは、**読み取り専用の層**の、積み重ね。実行時に、その上に、**書き込み可能な層**が、1 つ乗る。ファイルを変更すると、下の層から、書き込み層に**コピー**され(コピーオンライト。第2回の `fork` と、同じ考え方)、そこが変更される。

- 利点: 層は、共有され、**配布が、差分だけで済む**。起動が速い(コピーしない)。
- 注意: 書き込み層への書き込みは、遅い(コピーアップ)。コンテナが消えると、消える。**永続的なデータは、ボリューム**に置く(第5回の、`fsync` の議論は、ボリュームの、ファイルシステムに適用される)。

### 6.5 仮想マシンとの比較

| | コンテナ | 仮想マシン(VM) | マイクロVM / サンドボックス |
|---|---|---|---|
| カーネル | **ホストと共有** | **ゲスト専用** | ゲスト専用(最小)、またはユーザ空間で、システムコールを処理 |
| 起動 | ミリ秒〜秒 | 数秒〜数十秒 | 約 100 ms 程度、と説明される(Firecracker の論文。実装による) |
| 隔離の強さ | 弱い(カーネルの攻撃面が大きい) | 強い(ハイパーバイザの攻撃面は、小さい) | 強い〜中 |
| オーバーヘッド | 小さい | 大きい(ゲスト OS のメモリなど) | 小さい |
| 例 | Docker、runc | KVM、Xen | Firecracker(AWS Lambda、Fargate)、gVisor(Google) |

**複数の利用者が、同じ計算機で、信頼できないコードを動かす**(クラウドの関数実行)ときは、コンテナだけでは、隔離が、不十分とされ、**マイクロVM**や、**ユーザ空間のカーネル**(gVisor)が、使われる。**これは、隔離の強さと、密度(1 台に載る数)の、交換**である。

> **macOS の Docker**: 名前空間と cgroup は、Linux のカーネルの機能。macOS では、**Docker Desktop が、裏で、小さな Linux の仮想マシンを動かし**、その中で、コンテナを動かしている。したがって、macOS 上の「コンテナ」は、**VM の上の、コンテナ**であり、この Mac では、ネイティブには、動かせない。この回の、コンテナの演習の一部が、シミュレーションと、「Linux 専用・未実行」になっている理由。

## 7. CPU のスロットリング

### 7.1 CFS 帯域制御

`cpu.max = 200000 100000`(= 2 CPU)の意味を、正確に述べる。

> **周期 100 ms ごとに、グループ全体で、合計 200 ms の CPU 時間だけ、使える**。使い切ると、**その周期の残りの間、グループ内の全スレッドが、止まる**(スロットリング)。次の周期で、再開する。

「2 CPU 相当」と言われるが、**平均**の話であって、**瞬間**の話ではない。8 コアの計算機で、8 スレッドが、並行に走れば、**25 ms で、200 ms を使い切る**。残りの 75 ms は、止まる。

### 7.2 シミュレーション(演習5)

モデル: 1 ms ずつ進める。リクエストは、ポアソン到着、1 件の CPU 時間は、20 ms。上限は、200 ms / 100 ms(2 CPU)。同時に走れるスレッド数 T を変える(Go では、`GOMAXPROCS`)。600 秒分。

**これは、挙動を理解するための、モデル**である。実際のカーネルの、スケジューラの詳細(スライス、複数のコアへの、クォータの配分)は、省いている。

| 平均の使用率(上限に対して) | T | p50 | p99 | 最大 | スロットリングされた周期 |
|---|---|---|---|---|---|
| 30% | 2 | 20 | 37 | 63 | 0.0% |
| 30% | 8 | 20 | 20 | 35 | 0.1% |
| 50% | 2 | 20 | 50 | 83 | 0.5% |
| 50% | 8 | 20 | 22 | 71 | 1.9% |
| 70% | 2 | 23 | 81 | 158 | 8.9% |
| 70% | 8 | 20 | 55 | 173 | 14.6% |
| 90% | 2 | 46 | 235 | 410 | 49.7% |
| 90% | 8 | 20 | 218 | 405 | 57.3% |

(時間の単位は ms。T = 4、16 は、`go run ./ex5_cfs_throttle_sim` で見られる。)

読み取れること(モデルの範囲で):

1. **平均の使用率が、70% でも、14.6% の周期が、スロットリングされた**(T=8)。平均が、上限より低くても、**瞬間的な、重なり**で、クォータを使い切る周期が、出る。
2. **使用率 90% では、周期の約半分が、スロットリング**され、p99 は、最低の 20 ms の約 **10 倍**(約 220 ms)になった。最大は、約 400 ms(= 周期 100 ms の、数個ぶんの待ち)。
3. **スレッド数 T を増やすと、スロットリングされる周期は、増えた**(50% で、0.5% → 1.9%)。**しかし、このモデルでは、p99 は、T が大きいほうが、同じか、良かった**(T=2 は、スレッドの待ち行列で遅れ、T=8 は、スロットリングで遅れる、という、遅れ方の違い)。**「スレッドが多いほど、悪い」とは、この実験では、示せなかった**。当初の予想(T が多いほど、p99 が悪くなる)は、このモデルでは、確認できなかった(§10)。
4. 高い使用率では、**上限そのものが、支配的**で、T を変えても、p99 は、大きく変わらない。

**実務上の含意**(これは、モデルからの推論であり、実システムでの検証は、別に必要):

- **CPU の上限は、平均ではなく、周期の中の、瞬間的な量として、効く**。遅延の裾を気にするサービスでは、**CPU の `limit` を、設定しない**(`requests` だけにする)、という運用も、広く議論されている。
- Go では、`GOMAXPROCS` が、コンテナの CPU 上限を、考慮しないと、ホストのコア数になる。**新しいバージョンの Go(1.25 以降、要確認)では、cgroup の上限を、考慮する**よう、変更された、とされる。使っているバージョンで、`GOMAXPROCS` の値を、確かめること(`linux_only/cgroup_probe.go`)。
- スロットリングは、`cpu.stat` の `nr_throttled`、`throttled_usec` で、観測できる。

## 8. コンテナのネットワークと、Kubernetes

### 8.1 コンテナのネットワーク

各コンテナは、自分の NET 名前空間を持つ。ホストと、つなぐ方法:

| 方式 | 仕組み | 特徴 |
|---|---|---|
| ブリッジ + veth | コンテナと、ホストの間に、仮想のイーサネットケーブル(veth のペア)。ホスト側は、仮想ブリッジに、つながる | 既定。外へは、**NAT**(第7回)で出る。外から入るには、ポートの公開(DNAT) |
| ホストネットワーク | 名前空間を共有 | 速い。隔離なし |
| オーバーレイ | 複数のホストの間で、パケットを、別のパケットで包んで(カプセル化。VXLAN など)運ぶ | ホストをまたぐ、1 つの仮想ネットワーク。**カプセル化のオーバーヘッド**と、MTU の減少(第7回) |
| ルーティング型(BGP など) | ホストが、コンテナのサブネットを、BGP で広告 | カプセル化なし。ネットワーク機器の協力が要る(第10回) |

**MTU**: オーバーレイで、ヘッダが増えると、有効な MTU が、減る。**第7回の、MTU の黒穴**が、コンテナの環境でも、起きうる。

### 8.2 Kubernetes と、カーネルの設定

Kubernetes は、多数のホストに、コンテナを、スケジュールし、管理する。この回では、**カーネルの設定との対応**だけを見る。

| Kubernetes の設定 | カーネルでは | 意味 |
|---|---|---|
| `resources.requests.cpu` | `cpu.weight`(取り合いのときの比率)、**スケジューラが、ノードに載せる判断に使う** | 「最低これだけは、欲しい」 |
| `resources.limits.cpu` | `cpu.max` | スロットリングの、上限(§7) |
| `resources.requests.memory` | スケジューリングの判断。(メモリ QoS の、設定による) | |
| `resources.limits.memory` | `memory.max` | 超えると、OOM で、**exit 137**(§6.3) |

**QoS クラス**(ノードのメモリが足りないとき、誰を先に、追い出すか): `requests` と `limits` が、等しい(Guaranteed)> 一部が設定(Burstable)> 何も設定しない(BestEffort)、の順に、守られる。

**プローブ**: `liveness`(死んでいる → 再起動)、`readiness`(準備ができた → トラフィックを受ける)、`startup`(起動中)。**第10回のヘルスチェック**と、同じ考え方。`liveness` を、厳しくしすぎると、**負荷が高いとき、再起動の連鎖**が起きる(第15回)。

**プロセスの終了**: コンテナが、停止するとき、Kubernetes は、プロセスに `SIGTERM` を送り、一定時間(既定 30 秒)待って、`SIGKILL` を送る。**アプリは、`SIGTERM` で、新しい接続の受付をやめ、処理中のリクエストを終えてから、終わる**(グレースフル・シャットダウン)必要がある。

**PID 1 の問題**: コンテナの最初のプロセスは、PID 1 であり、(1) 孤児になった子プロセスの、**回収**(第3回の、ゾンビ)の責任を持つ。(2) **シグナルの、既定の処理が、通常のプロセスと違う**(ハンドラが無いと、`SIGTERM` が、無視されうる)。Go のプログラムを、直接 PID 1 にするなら、`SIGTERM` を、明示的に処理する。

**サービスディスカバリ**(第10回の続き): Kubernetes の `Service` は、複数の Pod を、1 つの、仮想的な IP(ClusterIP)に、まとめる。**kube-proxy**(または、eBPF)が、その IP への通信を、Pod に、**L4 で振り分ける**(第10回)。名前は、クラスタ内の DNS(**CoreDNS**)が、`service.namespace.svc.cluster.local` を、ClusterIP に解決する。**Ingress** は、外から、クラスタ内への、**L7 の入口**。サービスメッシュは、サイドカーが、各 Pod の通信を、受け持ち、L7 の、振り分け、再試行、観測を行う(第10回の L7 ロードバランサの、分散版)。

## 9. 博士レベルの論点

答えが定まっていない問い。口頭試問でも議論する。

1. **GC の、理論的な限界**: 並行 GC で、**停止の上限を、保証できるか**(リアルタイム GC。Bacon らの研究)。保証するために、スループットを、どれだけ失うか。
2. **世代別 GC は、Go に、有利か**: §2.6 のモデルは、「95% が、すぐ死ぬ」を、仮定した。Go のプログラムは、値型とスタック割り当てが多く、ヒープに来るオブジェクトの寿命の分布が、違う、という議論がある。**実際の、ヒープの寿命の分布を、測る**には、どうすればよいか。
3. **GC と、遅延の裾**(§4.4): STW が短いのに、p99 が悪化した。**ランタイムの、スケジューラと、GC のワーカーの、協調**を、どう設計すれば、裾を、抑えられるか。**測定の方法そのもの**(タイマーのずれ、処理の遅延)が、何を測っているのかも、考える。
4. **手動管理 vs GC**: Rust の、所有権による、コンパイル時の管理は、GC の、実行時のコストを、なくす。**代償**(学習コスト、設計の制約)は、何か。**GC のコストは、実際に、どの用途で、支配的になるか**。
5. **メモリの上限という設計**: メモリは、CPU と違い、「待てば、解決」しない。**ソフトな上限**(`GOMEMLIMIT`)と、**ハードな上限**(`memory.max`)の、**二重の仕組み**が、必要なのは、なぜか。**OOM を、どう設計に、組み込むか**(再起動を、前提とする)。
6. **コンテナの隔離**: 名前空間と cgroup は、**カーネルの、攻撃面を、共有する**。ユーザ空間のカーネル(gVisor)や、マイクロ VM(Firecracker)は、**何を、どれだけ、守るのか**。**コストは**。
7. **CPU の制限の、公平性**: CFS の帯域制御は、**平均の資源**を保証するが、**遅延**を保証しない(§7)。**遅延に敏感なサービスの、資源管理**は、どうあるべきか(固定の CPU の割り当て、`cpuset` による、専有)。
8. **「コンテナ」という抽象の、限界**: コンテナは、「軽い VM」として、理解されるが、**カーネルの機能の、集合**である。この誤解が、運用の事故(`/proc` の、ホストの値を見る、`NumCPU` が、ホストのコア数を返す、など)を、生む。**抽象の、漏れ**(leaky abstraction)は、どう、避けるか。

## 10. 演習の実測結果と、つまずいた点

実行環境: macOS(Apple シリコン)、Go のランタイム。**コンテナの機能は、実行していない**。

### 実測の要約

| 演習 | 内容 | 主な結果 |
|---|---|---|
| 1 | `GOGC` と、生きている量を変えて、GC のコストを測る | `GOGC` 25 → 400 で、GC の CPU 割合 72% → 13%、ヒープの最大 160 MB → 2270 MB。**生きている量によらず、GC の CPU 割合は、約 50%(`GOGC=100`)** |
| 2 | GC の時間と、遅延 | ポインタなし 400 MB = 0.11 ms、ポインタだらけ 400 MB = 28 ms。STW は 21〜36 µs。**ポインタだらけで、p99 のずれが、約 20 ms** |
| 3 | おもちゃの GC | コピーは、約 3 倍速い(メモリは 2 倍)。マーク & スイープ後の最大の連続した空き = 31 個(空き 70 万個のうち)。参照カウントの循環の漏れ = 50.0%。世代別で、コピーが約 10 分の 1(モデル) |
| 4 | `GOMEMLIMIT` | 上限を締めると、ヒープは、上限に近づくが、アプリの進みは、約 6 分の 1 に。**上限が、生きている量より小さいと、守れない** |
| 5 | CPU スロットリングの、シミュレーション | 平均 70% でも、14.6% の周期が、スロットリング。使用率 90% で、p99 は、約 10 倍 |
| (Linux 専用) | 名前空間、cgroup | **未実行** |

### つまずいた点と、確かめられなかったこと

1. **演習1: ヒープの最大が、理論値(生きている量 × (1 + GOGC/100))を、大きく上回った**。例えば `GOGC=400` で、理論値の約 4.5 倍(2270 MB 対 500 MB)。**仮説**(GC の最中に、アプリが、割り当てを続ける)は、**ありうるが、確かめていない**。この仮説なら、「割り当ての速度が、遅ければ、理論値に近づく」はずだが、別の割り当て速度では、試していない。
2. **演習2 B: ポインタだらけで、タイマーの p99 が、約 20 ms**。STW(数十 µs)では、説明できない。`GOMAXPROCS` を変えても残った。**仮説は、「全 P が、ふさがり、タイマーを待つ goroutine が、実行されない」だが、`runtime/trace` で、直接は、確かめていない**。
3. **演習3: 「生きている割合」の指定が、実際の到達可能な割合と、一致しなかった**(指定 50% で、実際は約 30%)。おもちゃのヒープの、作り方に、起因する。表は、実際の割合で読む(§2.5)。
4. **演習4: GC の CPU 割合が、70% を超えた**。CPU リミッタの目標(約 50%)と、食い違うように見える。**指標の定義に、アイドル時間の GC が含まれる可能性が、あるが、確かめていない**。
5. **演習5: 当初の予想(スレッド数が多いほど、p99 が悪化)が、モデルでは、確認できなかった**。モデルでは、スレッドが、少なければ、スレッドの待ち行列で、多ければ、スロットリングで、遅れる。**実際の Go のランタイム、実際のカーネルでの、挙動は、別に確かめる必要がある**。
6. **コンテナ(名前空間、cgroup)は、この Mac では、実行できない**。§6〜§8 の、仕様に関する記述は、**公開された知識**であり、この講義の実測では、ない。`linux_only/` のコードは、`cgroup_probe.go` の、`GOOS=linux go vet`(コンパイルチェック)だけを通した。`ns_demo.c` は、コンパイルも、していない。
7. **Docker を、使わなかった**: この Mac の、既存の Docker の環境に、手を入れないため。コンテナの実測が必要なら、Linux の環境で、`linux_only/README.md` の課題を、実行すること。

## 12. まとめ

- **GC は、到達可能性を、近似として使う**。**参照カウント**は、すぐ解放するが、**循環を漏らし**(演習3: 50.0% が漏れた)、更新のたびに、コストがかかる。**マーク & スイープ**は、ヒープ全体の走査と、**断片化**(空き 70 万個で、最大の連続 31 個)の代償。**コピー**は、生きているものだけを触り、詰まるが、**メモリが 2 倍**。**世代別**は、「若いものは、すぐ死ぬ」を使うが、**書き込みバリア**が要る。
- **並行 GC**は、アプリが、グラフを書き換えるので、**書き込みバリア**で、生きているものを、見落とさないようにする。アプリが速く割り当てると、**アシスト**で、アプリが、遅くなる。
- **Go の GC** は、**並行、非世代別、非移動**。`GOGC` は、**CPU とメモリの交換レート**(演習1: GC の CPU 割合 72% → 13%、ヒープ 160 MB → 2270 MB)。**GC のコストは、生きている、ポインタの量に比例**(ポインタなしの 400 MB で 0.11 ms、ポインタだらけで 28 ms)。**STW は、数十 µs だが、ポインタだらけのヒープでは、遅延の p99 が、約 20 ms に悪化した**(原因の仮説は未検証)。
- **`GOMEMLIMIT`** は、メモリの絶対的な上限への、**ソフトな目標**。締めるほど、メモリと引き換えに、アプリが遅くなる(約 9 → 1.4 GB/秒)。**生きている量より小さいと、守れない**。
- **コンテナ**は、**名前空間(見えるもの)、cgroup(使える量)、overlayfs(層)**の組み合わせで、**カーネルを共有する、普通のプロセス**。VM より軽いが、**隔離は弱い**。macOS の Docker は、**裏で Linux の VM**を動かす。
- **CPU の上限**は、**周期あたりの量**で、平均が低くても、**瞬間の重なり**で、スロットリングされる(モデル: 平均 70% で、14.6% の周期)。**メモリの上限は、ハード**で、超えると、`exit 137`。**Kubernetes の `limits` は、この 2 つのカーネルの設定そのもの**。
- **何が測れて、何が測れなかったか**を、区別する。この回は、**GC の実測と、シミュレーション**が中心で、**コンテナは、仕様の説明**。確かめられていない仮説は、§10 に、書いた。

次回(第12回)は、**分散システムの理論**に入る。複数の計算機が、協調するとき、**時計、順序、故障**は、どう扱われるのか。ここまでの、**1 台の中**の話から、**ネットワークをまたぐ**話へ。
