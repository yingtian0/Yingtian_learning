## 解答のヒント(まず見ずに答える)

**1.** 解放し忘れ(リーク)、解放後の使用(use-after-free)。到達可能性(根から、ポインタをたどって、到達できるか)。到達できても、もう使わないものは、残る(近似)。逆はない(安全)。

**2.** 利点: すぐ解放、停止がない。欠点: 循環を回収できない、更新のたびにコスト(マルチスレッドでアトミック)。輪(循環)は、互いに参照しあい、カウントが 0 にならない。

**3.** マーク: 生きている量。スイープ: ヒープ全体。

**4.** 良い: 生きているものだけを触る、詰まる(断片化しない)、確保が速い。悪い: 半分の領域が空く(メモリ 2 倍)、ポインタの書き換えが要る。生きている割合が低いと、触る量が、少ないので、ヒープ全体を走査する、マーク & スイープとの、差が大きい。

**5.** 空きの合計は足りても、連続した領域が確保できない(外部断片化)。コピーは、生きているものを詰めて、残りを 1 つの連続した空きにする。

**6.** 大半のオブジェクトは、若くして死ぬ。若い世代は、生き残りが少ないので、コピーが安い。老いた世代から若い世代への参照を、記録する仕組み(書き込みバリア、カードテーブル)。

**7.** 「95% が、すぐ死ぬ」という仮定(寿命の分布)。そのまま当てはめてはいけない。バリアのコストも、含まれていない。

**8.** ヒープが大きいほど、マークが長く、アプリを止める時間が長くなる(STW の長さは、生きている量に比例)。並行なら、アプリが走りながら、マークできる。

**9.** 白=未訪問、灰=発見したが、未走査、黒=走査済み。見落とし: 黒が白を指す、かつ、灰から白への経路が、すべて断たれる。

**10.** ポインタの書き込みに、ランタイムが挿入する小さなコード。挿入型は、「黒 → 白」を防ぐ(指される白を灰に)。削除型は、経路が断たれることを防ぐ(消される先を灰に)。代償: GC が動いている間、書き込みが遅い。

**11.** 割り当てが多い goroutine に、GC の仕事を手伝わせる。アプリが GC より速く割り当てると、GC が追いつかないため。アプリには、割り当てが、遅くなったように見える。

**12.** 並行(停止が短い。CPU と、書き込みバリアのコスト)、世代別でない(単純。若いゴミを効率よく集められない)、動かさない(cgo、書き換え不要。断片化はアロケータが、サイズクラスで対処)。

**13.** ヒープの目標 ≈ 生きている量 × (1 + GOGC/100)。25 → 400 で、GC の CPU 72% → 13%、ヒープ 160 → 2270 MB、割り当て速度 2.46 → 14.64 GB/秒。CPU とメモリの交換。

**14.** 1 回の GC のコストは、生きている量に比例(4 倍)。頻度は、割り当て速度 ÷ 生きている量なので、約 4 分の 1。掛け合わせると、一定。(割り当て速度が、同じなら、割合は、`GOGC` だけで決まる。)

**15.** 仮説: GC のマーク中も、アプリが、割り当て続け、目標を超える。確かめていない(割り当て速度を変えた実験を、していない)。

**16.** ポインタを含まないデータは、GC が中身を走査しない。ポインタだらけは、全部、たどる。ポインタのない、大きな配列に詰めると、GC のコストが、ほぼゼロ。代償は、デバッグしにくさ、設計の制約。

**17.** STW は、根を集めるときと、マークの終了の確認だけ。ヒープ全体を、たどる作業は、並行に行われる。

**18.** 確か: STW は数十 µs。p99 は約 20 ms(`GOMAXPROCS` を変えても残った)。仮説: 全 P が、GC とアプリでふさがり、タイマーの goroutine が、実行されない(スケジューリングの遅延)。確かめる方法: `runtime/trace`、`gctrace`、goroutine の「実行可能だが未実行」の時間。

**19.** 変数が関数の外に逃げるか、静的に調べ、逃げなければスタックに置く。`go build -gcflags=-m`。`sync.Pool` は、GC で中身が捨てられうる、キャッシュ。「必ず残る」資源には使えない。

**20.** `GOGC` は相対(生きている量の何倍)、`GOMEMLIMIT` は絶対(合計の目標)。コンテナの `memory.max`(絶対)に、合わせる(上限の 90% 前後が目安、アプリごとに測る)。

**21.** 締めるほど、ヒープは上限に近づき、GC が増え、割り当て速度は、約 9 → 1.4 GB/秒に落ちた。80 MiB では守れなかった(138 MB)。ソフトな目標で、OOM を防ぐ保証ではない。

**22.** 説明できなかった。仮説(指標にアイドルな P の GC 時間が含まれる)は、あるが、確かめていない。リミッタの効き方は、確認できていない。

**23.** 名前空間、cgroup、ファイルシステムの層(+ ケーパビリティ、seccomp)。新しい種類のカーネルの機能ではなく、既存の機能の組み合わせで、中身は、普通のプロセス。

**24.** 名前空間は、見えるものを分ける(隔離)。cgroup は、使える量を制限する(制限)。

**25.** USER 名前空間で、内の root = 外の一般ユーザ。しかし、カーネルは共有なので、カーネルの脆弱性が、隔離を破りうる。

**26.** 回収しても足りないと、OOM キラーが SIGKILL(exit 137 = 128 + 9)。CPU は、待たせれば解決するが、メモリは、待たせても、解決しない。

**27.** `memory.high` はソフト(超えると、回収が強まり、遅くなる)。`memory.max` はハード(OOM)。

**28.** ファイルを変更すると、下の層から書き込み層にコピー(fork の COW と同じ)。書き込み層は、コンテナと共に消える。永続データは、ボリューム。

**29.** コンテナ: カーネル共有、隔離が弱い、軽い。VM: ゲスト専用のカーネル、強い、重い。マイクロ VM(Firecracker)/ gVisor: 強い〜中、軽い。信頼できないコードには、マイクロ VM、ユーザ空間のカーネル。隔離の強さと密度の交換。

**30.** Docker Desktop が、裏で Linux の VM を動かし、その中でコンテナを動かす。VM の上のコンテナ。名前空間と cgroup が、macOS に無いため、実行しなかった。

**31.** 周期 100 ms あたり、全体で合計 200 ms の CPU 時間。平均の話で、瞬間の話ではない。8 スレッドが並行だと、25 ms で使い切り、残り 75 ms は、全スレッドが停止。

**32.** 瞬間的な重なりで、周期の中の合計が、クォータに達する周期が出る。90% では、p99 が、約 10 倍(約 220 ms)。

**33.** 確認できなかった。T が多いと、スロットリングは増えたが、p99 は、T=2 より、同じか良かった(T=2 は、待ち行列で遅れる)。モデルは、スケジューラの詳細を、省いている。

**34.** 利点: スロットリングが起きない(遅延の裾)。危険: 隣のコンテナに、CPU を奪われる、取り合いの公平性が、`requests` だけに、依存する。Go の `GOMAXPROCS` は、古いバージョンでは、ホストのコア数。新しいバージョン(1.25 以降、要確認)は、cgroup の上限を考慮。

**35.** `requests.cpu` → `cpu.weight` とスケジューリング、`limits.cpu` → `cpu.max`、`limits.memory` → `memory.max`。QoS クラスは、ノードのメモリ不足のとき、誰から追い出すか。

**36.** SIGTERM → 猶予(既定 30 秒)→ SIGKILL。新しい接続を止め、処理中を終える。PID 1: 孤児の回収(ゾンビ)、シグナルの既定の処理が違う(ハンドラがないと SIGTERM が無視されうる)。

**37.** 負荷が高く、応答が遅れると、プローブが失敗し、再起動される。再起動で、さらに負荷が集まり、連鎖する(第10回の、ヘルスチェックと再試行の嵐、第15回)。

**38.** コンテナの外へは NAT、ホスト間のオーバーレイは、ヘッダ分 MTU が減り、黒穴の問題が起きうる。

**39.** `kubectl describe` の `OOMKilled`、`memory.current`、ヒープのプロファイル、ヒープ以外の使用量(スタック、cgroup のページキャッシュ)。対策: `GOMEMLIMIT` の設定(上限の 90% 前後)、リークの修正、上限の見直し。ただし、ヒープが上限より大きいと、守れない。

**40.** GC(`gctrace`、ポインタの量)、CPU スロットリング(`cpu.stat` の `nr_throttled`)、ネットワーク、ロック競合。GC とスロットリングは、同時に起きうる。

**41.** 利点: GC のコストがほぼゼロ。代償: デバッグしにくい、設計の制約、手動の管理が増える。

**42.** 例: ヒープが理論値を超えた理由、p99 の 20 ms の原因、GC の CPU 割合が 70% を超えた理由、コンテナの実挙動、スレッド数と p99 の関係(実システム)。確かめ方は、それぞれ、本文 §10。
