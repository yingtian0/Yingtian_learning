# 第12回 分散システムの理論

> ステータス: 執筆済み(第1版)
> 前提: 第4回(アトミック操作、メモリ順序)、第8回(TCP、タイムアウト)、第10回(ヘルスチェック、再試行、一貫性ハッシュ)、第11回(GC の停止、スロットリング)
> 演習言語: Go
> 所要目安: 本文 4時間 + 演習 5〜6時間
> **演習はすべて、自分のマシン内の、シミュレーション(確率モデルと、離散的な模擬)。実際のネットワーク、実際のデータベースは、使っていない。数値は、モデルの結果であり、実システムの値ではない。**

## この回のゴール

この回を終えると、次のことが説明できるようになる。

1. 1 台のマシンと、複数のマシンで、**何が根本的に違う**のか(部分的な故障、共有の時計がない、遅延に上限がない)。
2. 「同時」「先」とは、何を意味するのか。Lamport 時計、ベクタークロック、HLC、TrueTime は、それぞれ、何を保証し、何を保証しないか。
3. 「遅い」と「死んでいる」を、なぜ、外から区別できないのか。故障検出器は、何と何を交換するのか。
4. 線形化可能性、逐次一貫性、因果一貫性、結果整合性は、何が違うのか。クォーラム(R + W > N)は、何を保証するのか。**しないのか**。
5. CAP 定理は、正確には、何を主張するのか。よくある誤解は、何か。PACELC は、何を足すのか。
6. FLP の不可能性は、何を主張し、何を主張しないのか。

第1〜11回は、**1 台の計算機の中**と、**2 台をつなぐ通信**を扱った。この回から、**多数の計算機が、協調して、1 つのシステムに見える**ための、理論に入る。理論の回なので、定理の、**正確な主張**を、大切にする。

## 1. 動機: なぜ、1 台と根本的に違うのか

### 1.1 3 つの違い

1 台のプログラムでは、関数を呼べば、**成功するか、失敗するか**のどちらかが、すぐに分かる。時計は、1 つ。メモリは、共有。

複数の計算機では、次の 3 つが、成り立たない。

| | 1 台 | 複数台 |
|---|---|---|
| **部分的な故障** | プロセスが落ちれば、全部が落ちる | **一部だけ**が落ちる。他は、動き続ける。落ちたのか、遅いだけなのか、分からない |
| **共有の時計** | 1 つの時計 | 各マシンの時計が、**ずれる**。どちらが先かを、時計で決められない |
| **共有のメモリ** | 同じメモリを、読み書き | **メッセージ**だけ。メッセージは、遅れる、失われる、重複する、順序が入れ替わる |

特に、**応答がない**とき、次のどれか、見分けられない(§4)。

1. 要求が、相手に届かなかった。
2. 相手が、要求を処理して、応答が、届かなかった(処理は、済んでいる!)。
3. 相手が、遅い(まだ処理中)。
4. 相手が、落ちた。

第8回の TCP も、第10回の再試行も、この不確実さへの対処だった。**再試行すると、2 の場合に、二重に処理される**(冪等性が要る、第10回)。

### 1.2 分散コンピューティングの、8 つの誤り

Peter Deutsch らが、まとめた、新人が、思いがちな、誤った仮定。

1. ネットワークは、信頼できる。2. 遅延は、ゼロ。3. 帯域は、無限。4. ネットワークは、安全。5. トポロジーは、変わらない。6. 管理者は、1 人。7. 転送のコストは、ゼロ。8. ネットワークは、均質。

この回の理論は、**これらを、仮定せず**に、何が、できて、何が、できないかを、示す。

## 2. システムモデル

理論は、**モデル**(何を仮定するか)を、先に決める。**同じ問題が、モデルによって、解ける、解けない**が、変わる。

### 2.1 タイミングのモデル

| モデル | 仮定 | 現実との関係 |
|---|---|---|
| **同期** | メッセージの遅延と、処理の時間に、**既知の上限**がある | 厳しい。実際のネットワークでは、上限を、保証できない |
| **非同期** | 遅延に、**上限がない**(必ず届くが、いつかは不明) | 最も弱い仮定。**安全側**。ただし、できることが、少ない(FLP、§6) |
| **部分同期** | 上限は、ある。しかし、**未知**。または、**いつかから、成り立つ** | **現実的**。Dwork、Lynch、Stockmeyer (1988)。第13回の、Paxos や Raft は、このモデルで、動く |

### 2.2 故障のモデル

| 故障 | 内容 | 例 |
|---|---|---|
| **クラッシュ停止** | 止まったら、二度と動かない | 単純なモデル |
| **クラッシュ・リカバリ** | 止まっても、再起動して、**ディスクの状態から**、復帰する | 現実的。第5回の `fsync` が、重要になる |
| **欠落(オミッション)** | メッセージを、送らない、受け取らない | パケットの喪失 |
| **ビザンチン** | **任意の、嘘や、誤った動作**をする | バグ、悪意、ビットの反転 |

故障のモデルが、**強いほど**(ビザンチン)、必要なノードの数が、**増える**。クラッシュ停止に耐えるには、f 個の故障に対して、**2f + 1** ノード(多数派)。ビザンチンには、**3f + 1**(第13回)。

### 2.3 通信のモデル

ネットワークは、メッセージを、失う、重複させる、並べ替える。その上に、**再送**と**重複の排除**を、重ねると、「**いつかは、1 回だけ、届く**」という、より強い通信が作れる(TCP が、1 対 1 で、していること、第8回)。ただし、**相手が落ちたままなら、永遠に届かない**。

## 3. 時間と順序

### 3.1 物理時計は、ずれる

各マシンの時計は、水晶発振器で、**ずれていく**(ドリフト。一般に、数十 ppm 程度とされる。**温度など、条件による。具体的な値は、製品の仕様と、実測で確認すること**)。NTP で、定期的に、補正するが、補正の精度は、ネットワークの遅延の非対称性などに、制限される。**ミリ秒の誤差を、前提にするのが、安全**。

### 3.2 「最後の書き込みが勝つ」(LWW) の、危険(演習2 A)

複数のレプリカで、同じキーへの書き込みが、競合したとき、**時刻の大きいほうを残す**(LWW)方式は、単純で、広く使われる。しかし、**時刻が、ノード間でずれていると、本当に後の書き込みが、負ける**。

**演習2 A**: 2 つのノードの、時計のずれが、標準偏差 σ の正規分布。真の時刻で、Δ ms 後に、別のノードが書いたとき、**後の書き込みが負ける確率**。

| Δ \ σ | 0.1 ms | 1 ms | 10 ms | 50 ms |
|---|---|---|---|---|
| 0.5 ms | 0.02% | 36.15% | 48.46% | 49.88% |
| 2 ms | 0.00% | 7.84% | 44.37% | 48.95% |
| 10 ms | 0.00% | 0.00% | 23.82% | 44.27% |
| 50 ms | 0.00% | 0.00% | 0.03% | 24.08% |
| 200 ms | 0.00% | 0.00% | 0.00% | 0.23% |

書き込みの間隔が、時計のずれと、同程度以下なら、**ほぼ、コイン投げ**(最大 50%)に近づく。**負けた書き込みは、エラーも出ずに、失われる**。

### 3.3 happened-before(Lamport、1978)

時計を、あきらめて、**因果関係だけ**で、順序を、定義する。

> **a → b**(a が b より先に起きた)とは、次のどれか。
> 1. 同じプロセスで、a が b より前。
> 2. a が、メッセージの**送信**で、b が、その**受信**。
> 3. a → c かつ c → b(推移的)。
>
> a → b でも b → a でもないとき、a と b は**並行**(concurrent)。

「並行」は、「同時刻」では**ない**。**情報が、一方から他方へ、伝わりえなかった**、という意味。

### 3.4 Lamport 時計

各プロセスが、整数のカウンタ L を持つ。

- イベントのたびに、L を 1 増やす。
- 送信するメッセージに、L を付ける。
- 受信したら、L = max(自分の L, メッセージの L) + 1。

**性質**: **a → b ならば L(a) < L(b)**。

**逆は、成り立たない**: L(a) < L(b) でも、a → b とは限らない。**並行なイベントにも、数値の大小は、付いてしまう**。

### 3.5 ベクタークロック

各プロセスが、**全プロセスの、カウンタの組** V = (V₁, …, Vₙ) を持つ。

- 自分のイベントで、自分の成分を、1 増やす。
- メッセージに V を付ける。受信したら、成分ごとに max を取り、自分の成分を 1 増やす。

**比較**: V(a) ≤ V(b)(全成分で ≤)かつ、V(a) ≠ V(b) なら、a → b。どちらの方向でも、成り立たなければ、**並行**。

**性質**: **a → b ⇔ V(a) < V(b)**。**因果関係と、並行を、正確に区別できる**。

**代償**: ベクタの大きさが、**プロセス数に比例**する。

### 3.6 演習1: 実測

5 つのプロセス、700 個のイベント、24 万 4,650 対のイベントの組。**正解は、メッセージのつながりから、独立に計算した、因果関係の推移閉包**。

| 項目 | 結果 |
|---|---|
| 正解: 因果関係あり / 並行 | 211,501 対(86.5%)/ 33,149 対(13.5%) |
| a → b なのに、L(a) ≥ L(b) | **0 対**(Lamport 時計は、因果関係と矛盾しない) |
| L(a) < L(b) の対のうち、実際は並行 | 27,252 / 238,753 = **11.4%** |
| ベクタークロックの判定が、正解と食い違い | **0 対** |

ベクタークロックの大きさ(整数 = 8 バイトとして): 5 プロセスで 40 バイト、100 で 800、1,000 で 8,000、10 万で 800,000 バイト。Lamport 時計は、常に 8 バイト。

**読み取れること**: Lamport 時計で「a が先」と言っても、**約 11% は、因果関係とは、無関係な順序**だった。ベクタークロックは、正確だが、**プロセスが多いと、重い**。実システム(Dynamo など)は、ベクタを**切り詰める**、または、**サーバーごと**に持つ、などの、工夫をする(§8 の、確かめていない点)。

### 3.7 HLC(ハイブリッド論理時計)

**物理時計に近い値**を持ちつつ、**因果的な順序を保つ**。タイムスタンプ = (l, c)。l は、「見た中で最大の物理時刻」、c は、同じ l の間の、論理カウンタ。受信時に、**受け取ったタイムスタンプより、大きい値**を、作る。

**演習2 B**(ノード 1 が書く → ノード 2 が、その結果を読んで書く、という、**因果的に順序づけられた**書き込み): 2 つ目の、タイムスタンプが、1 つ目より小さくなる割合。

| σ | 物理時計だけ | HLC |
|---|---|---|
| 1 ms | 14.93% | **0.00%** |
| 10 ms | 45.74% | **0.00%** |
| 50 ms | 49.19% | **0.00%** |

HLC は、**因果的な順序**は、時計がずれても、守る。**並行な書き込みの、真の時刻の順序**は、保証しない(Lamport 時計と同じ限界)。

### 3.8 TrueTime(Spanner)

時刻を、**1 点**ではなく、**区間** [earliest, latest] で返す。**真の時刻は、必ず、この区間の中にある**、ことを、保証する(GPS と原子時計を、データセンター内に置き、不確かさ ε を、小さく保つことで、実現するとされる。論文では、ε は、数 ms 程度と報告されている。**原典で確認すること**)。

**外部整合性**: T1 が、コミットを**完了してから**、T2 が始まったなら、T2 のタイムスタンプ > T1 のタイムスタンプ。守るために、**コミット待ち**(commit wait): トランザクションに、タイムスタンプ ts を選び、**ts が、確実に過去になる(earliest > ts)まで、完了を、返さない**。

**演習2 C**(モデル。時計のずれは、|オフセット| ≤ ε を、一様に満たす):

| ε | コミット待ちなし: 順序の逆転 | コミット待ちあり: 逆転 / 平均の待ち |
|---|---|---|
| 1 ms | 49.95% | 0.00% / 2.00 ms |
| 4 ms | 50.16% | 0.00% / 8.00 ms |
| 7 ms | 49.95% | 0.00% / 14.00 ms |
| 20 ms | 50.03% | 0.00% / 40.00 ms |

**注意**: これは、**ほぼ自明なモデル**である(待つ時間は、モデルの式から、ちょうど 2ε になる)。この実験が示すのは、**「待てば、逆転が消える。代償は、約 2ε」**という、**構造**であって、実際の Spanner の数値ではない。同じキーへの、直列なトランザクションの、上限の速度 ≈ 1 / (2ε)(ε = 7 ms で、約 70 回/秒、モデルの計算)。

> **要点**: 時間の不確かさは、**なくせない**。**不確かさを、明示して、待つ**(TrueTime)、**因果だけを使う**(論理時計、HLC)、**不確かさを無視して、失う**(LWW)、の 3 つの態度がある。

## 4. 故障検出

### 4.1 「遅い」と「死んでいる」

**応答がない**とき、相手が、死んでいるのか、遅いのか、**外から**は、見分けられない(§1.1)。**非同期のモデルでは、原理的に、不可能**。そこで、実用的には、**タイムアウト**を使い、「疑う」。**疑いは、間違いうる**(誤検出)。

故障検出器の、2 つの性質(Chandra と Toueg、1996):

- **完全性**: 落ちたノードを、**いつかは**、疑う。
- **正確性**: 落ちていないノードを、疑わない。

**この 2 つは、トレードオフ**になる(速く疑えば、誤検出が増え、疑いを遅らせれば、検出が遅い)。

### 4.2 演習3: タイムアウトの、トレードオフ

100 ms ごとの、ハートビート。遅延: 基本 5 ms + 対数正規のゆらぎ。さらに、確率 0.2% で、200〜2000 ms の停止(GC の停止、パケット喪失、スロットリングを想定。第8、11回)。**10 時間分**。

到着間隔: p50 = 100 ms、p99 = 104 ms、p99.9 = 1,183 ms、最大 = 2,096 ms。**ふだんは、安定しているが、まれに、10 倍以上、遅れる**(裾が重い)。

**固定のタイムアウト T**:

| T (ms) | 誤検出(10 時間の回数) | 検出時間(平均、概算) |
|---|---|---|
| 150 | 715 | 100 ms |
| 300 | 715 | 250 |
| 500 | 623 | 450 |
| 1,000 | 433 | 950 |
| 2,000 | 36 | 1,950 |
| 3,000 | 0 | 2,950 |

**φ(ファイ)累積検出器**(直近 1,000 個の間隔の平均と標準偏差、正規分布を仮定):

| φ の閾値 | 誤検出 | 検出時間(平均、概算) |
|---|---|---|
| 1 | 4,146 | 111 ms |
| 4 | 779 | 228 |
| 8 | 685 | 319 |
| 16 | 625 | 444 |

**読み取れること**:

1. **タイムアウトを、延ばすと、誤検出が減るが、検出が遅くなる**。0 にするには、約 3 秒(最大の遅れを、超える値)が要る。
2. **このモデルでは、φ 検出器は、固定のタイムアウトに、勝てなかった**(φ = 16 で、検出 444 ms、誤検出 625。固定 T = 500 で、検出 450 ms、誤検出 623。ほぼ同じ)。**原因の仮説**: φ 検出器は、間隔が、**正規分布**に従う、と仮定するが、このモデルの遅れは、**裾が重い**(まれな、長い停止)。**仮説であり、別の分布で確かめていない**。φ 検出器の、利点は、**遅延の平均が、時間と共に変わる**環境に、**自動で適応**する点にあり、この実験(定常な分布)は、その利点を、見せていない。
3. **同じ検出時間で、誤検出を減らす**には、**間隔の分布の、形**(裾の重さ)を、モデルに入れる必要がある。

> **設計上の含意**: タイムアウトは、**その環境の遅延の、裾**(p99.9 や最大)を、実測して、決める。**平均の何倍、という経験則は、裾が重い環境では、危うい**。

## 5. 不可能性

### 5.1 2 人の将軍

2 人の将軍が、信頼できない使者で、連絡し、**同時に攻撃**する、という合意を、したい。「攻撃する」と送る。届いたか、分からない → 確認を、送る。その確認が、届いたか、分からない → …。**有限の回数のメッセージでは、両者が、確実に同意した、と確信することは、できない**。**メッセージが、失われうる通信では、確定的な合意は、作れない**。

実用的には、**確実さを諦めて**(確率的に、十分な確信)、または、**失敗を許容する設計**(冪等性、補償)にする。

### 5.2 FLP の不可能性(Fischer、Lynch、Paterson、1985)

**正確な主張**:

> **非同期のシステム**で、**たった 1 つのプロセスが、クラッシュしうる**だけで、**決定的**(確率を使わない)な、合意のアルゴリズムで、**必ず終了することを保証する**ものは、存在しない。

**注意すべき点**:

- 「合意が、**不可能**」では、ない。**「必ず終了する(活性)ことを、保証できない」**。
- **安全性**(誤った合意をしない)は、**守れる**。**終わらない**、実行が、ありうる。
- **非同期のモデル**での結果。**部分同期**(§2.1)、**乱数**、**故障検出器**を使えば、回避できる。
- 現実の、Paxos や Raft は、**安全性を、常に守り**、**活性は、ネットワークが、しばらく安定すれば、得られる**、という設計(第13回)。

> FLP は、「分散合意は、実用上、できない」ではない。**「どんなタイミングでも、終わる、完璧なアルゴリズムは、ない」**。

## 6. 一貫性モデル

### 6.1 一貫性とは

**複数のレプリカ(コピー)**を、持つとき、**クライアントから見て、どのような振る舞いが、許されるか**の、約束。**強いほど、プログラムが、書きやすい**が、**遅く、可用性が低い**。

**用語の注意**: 「一貫性(consistency)」は、(1) ここの、レプリカの一貫性、(2) ACID の C(データの制約)、(3) CAP の C(線形化可能性)、で、意味が違う。

### 6.2 強い順

| モデル | 内容 |
|---|---|
| **線形化可能性**(Herlihy と Wing、1990) | 各操作が、**開始と応答の間の、ある 1 点で、瞬時に起きた**ように見える。**実時間の順序**を守る |
| **逐次一貫性**(Lamport、1979) | 全操作が、**1 つの順序**に並べられ、各クライアントの順序は守られる。**実時間とは、無関係** |
| **因果一貫性** | **因果関係のある**操作は、全員に、同じ順序で見える。**並行な操作は、人によって、順序が違ってよい** |
| **セッション保証**(Terry ら、1994) | 自分の書き込みを読める(read-your-writes)、読みが、戻らない(単調な読み)、など。**1 人のクライアントの視点** |
| **結果整合性** | 更新が止まれば、**いつかは**、全レプリカが、同じ値になる。それ以外の保証は、ない |

### 6.3 線形化可能性の検査(演習4)

**操作の履歴**(各操作の、開始時刻、応答時刻、値)が、線形化可能かを、Wing と Gong の方式の、深さ優先探索で、検査する。**まだ並べていない操作のうち、他の操作が、すでに終わっているものより、前に始まった操作だけを、次の候補にする**。読みは、直前の書き込みの値を、返さなければならない。

**モデル**: N = 3 のレプリカ。書き込みは、全レプリカに送り、W 個の ack を待つ。読みは、R 個のレプリカに問い合わせ、**最大のバージョン**の値を返す。4 クライアントが、3 操作ずつ(12 操作)の履歴を、4,000 個。

**操作の間の待ち = 1 ms(混んでいる)**:

| R | W | R + W > N | 線形化できない履歴 | 古い読み(読みの総数に対して) |
|---|---|---|---|---|
| 1 | 1 | いいえ | **96.4%** | 48.7% |
| 1 | 2 | いいえ | 35.7% | 3.3% |
| 2 | 2 | **はい** | **0.4%** | 0.0% |
| 1 | 3 | **はい** | **25.5%** | 0.0% |
| 3 | 1 | **はい** | 0.0% | 0.0% |
| 3 | 3 | **はい** | 0.0% | 0.0% |

**操作の間の待ち = 20 ms(空いている)**:

| R | W | R + W > N | 線形化できない履歴 | 古い読み |
|---|---|---|---|---|
| 1 | 1 | いいえ | 71.2% | 19.8% |
| 1 | 2 | いいえ | 15.8% | 1.9% |
| 2 | 2 | はい | 0.0%(1 / 4000) | 0.0% |
| 1 | 3 | **はい** | **8.8%** | 0.0% |
| 3 | 1 | はい | 0.0% | 0.0% |
| 3 | 3 | はい | 0.0% | 0.0% |

**読み取れること**:

1. **R + W ≤ N(クォーラムが交わらない)**では、**大きく崩れる**。R = 1、W = 1 は、混んでいると、**ほぼ全ての履歴が、線形化できない**。古い読みも、約半数。
2. **R + W > N でも、線形化可能とは、限らない**。**R = 1、W = 3**では、「古い読み」は **0%**(完了した書き込みは、全レプリカに届いているので)なのに、**25.5% の履歴が、線形化できなかった**。理由: 書き込みが**進行中**のとき、あるクライアントの読みが、**新しい値**を見て(更新済みのレプリカに当たった)、**その後**の、別のクライアントの読みが、**古い値**を見る(未更新のレプリカに当たった)。**新 → 旧、と戻る**。これは、**クォーラムの交わりだけでは、防げない**(R = 1 では、進行中の書き込みを、検出できない)。
3. **R = 2、W = 2** も、**0.4%** の履歴で、崩れた。**これも、進行中の書き込みに関する、同じ理由**と考えられる(確かめていない)。
4. **R = 3**(全レプリカに問い合わせる)なら、**0%**。ただし、**1 つでも、レプリカが落ちると、読みが、できなくなる**(可用性)。
5. 古い読み(完了した書き込みを、見ない)は、**R + W > N で、0** になった。**「古い読みがない」と「線形化可能」は、違う**。

> **R + W > N の、正確な保証**: 「**完了した**書き込みを、**必ず読める**」。それ以上ではない。**進行中の書き込みが、あるときの、読みの順序**は、別の仕組み(**読みの修復**(read repair)、書き込み前の読み、合意アルゴリズム)が、必要。

**このシミュレーションの、簡略化**(確かめている範囲の限界): バージョンは、**書き込みの開始の順**に、全体で一意(実際のシステムでは、コーディネータごとに、競合する)。ネットワークの遅延は、指数分布。履歴は、12 操作と短い。**実際の Dynamo 型のデータベースの、挙動を、再現するものではない**。

## 7. CAP と PACELC

### 7.1 CAP 定理の、正確な主張

Brewer(2000、予想)、Gilbert と Lynch(2002、証明)。

> **ネットワークの分断(P)が起きている間、1 つの**読み書き**可能なレジスタ(オブジェクト)について、**線形化可能性(C)と、可用性(A)を、同時には、満たせない**。

| 用語 | CAP での、正確な意味 |
|---|---|
| **C(一貫性)** | **線形化可能性** |
| **A(可用性)** | **生きている、全ての**ノードが、(分断されていても)、要求に、**いつかは、応答**する |
| **P(分断耐性)** | 分断が、起きても、システムは、動く |

### 7.2 よくある誤解

1. **「3 つのうち、2 つを選べ」**。→ 分断は、**選べない**(起きる)。**起きたときに、C と A の、どちらを諦めるか**、を選ぶ。分断が、起きていないときは、**両方を、満たせる**。
2. **「CP のシステムは、可用性が、ゼロ」**。→ **多数派の側は、動き続ける**(演習5)。
3. **「C は、ACID の C」**。→ 違う(§6.1)。
4. **「CAP は、システム全体を、CP か AP に、分類する」**。→ **操作ごと、データごと**に、異なりうる。
5. CAP の「A」は、**「応答が、遅くても、いつかは返る」**という、非常に弱い定義。**実用上の、可用性(遅延の目標)とは、違う**。

### 7.3 演習5: 分断の間

5 ノード。時刻 10〜20 秒に、{A, B, C} と {D, E} に分断。各ノードに、毎秒 1 回、書き込み(20 個のキーのどれか)。合計 150 件。

| | 成功した書き込み | 分断中 | 少数派側 |
|---|---|---|---|
| **CP**(多数派が必要) | 130 / 150(86.7%) | 30 / 50(60.0%) | **0%**(拒否) |
| **AP**(常に受け付ける) | 150 / 150(100%) | 50 / 50 | 100% |

**AP の、分断が直った後**: 両側が、分断中に書いたキーは、20 個のうち **9 個 → 競合**。

- **LWW で統合**: 9 件の書き込みが、**成功を返したのに、静かに失われた**(成功した 150 件の 6.0%)。
- **競合を保持(兄弟)**: 9 個のキーで、18 個の値が残る。**アプリが、マージする責任**を持つ(例: CRDT、購入カートの和集合)。

**CP**: 競合する値は、存在しない。**少数派の、クライアントは、拒否される**(エラーを受ける)。

> **分断を、無視できる設計は、ない。何を諦めるかを、先に決める**。「ユーザーの買い物かごは、AP でよい(後で、マージできる)。残高は、CP(二重に使えない)」など、**データの、意味**で決まる。

### 7.4 PACELC(Abadi、2012)

CAP は、**分断のときだけ**を、語る。**分断がないとき(通常時)にも、トレードオフがある**。

> **P**artition の間は、**A** と **C** の、どちらか。**E**lse(それ以外)は、**L**atency(遅延)と **C**onsistency(一貫性)の、どちらか。

**通常時の理由**: 強い一貫性には、**複数のレプリカとの、同期の通信**が要る。**遅延が増える**(地理的に離れたレプリカなら、光の速度で、数十〜百 ms。第1、7回)。**一貫性を弱めると、速くなる**。

| システムの分類(典型例。製品や設定による) | 分断の間 | 通常時 |
|---|---|---|
| PA/EL | 可用性 | 遅延 |
| PC/EC | 一貫性 | 一貫性 |
| PA/EC、PC/EL | 組み合わせ | |

## 8. 演習の実測結果と、つまずいた点

実行環境: macOS(Apple シリコン)、Go。**すべて、モデルのシミュレーション**。

### 実測の要約

| 演習 | 内容 | 主な結果 |
|---|---|---|
| 1 | Lamport 時計とベクタークロック | Lamport: a → b ⇒ L(a) < L(b) は 0 件の違反。**L の順序の 11.4% は、実は並行**。ベクタークロックは、正解と完全に一致 |
| 2 | 物理時計、HLC、TrueTime 風 | σ = 1 ms、Δ = 0.5 ms で、LWW は 36% 逆転。**HLC は、因果的な順序で、0%**。コミット待ちは、約 2ε |
| 3 | 故障検出 | タイムアウトを延ばすと、誤検出は減り(715 → 0)、検出は遅れる(100 → 2,950 ms)。**φ 検出器は、このモデルでは、固定と同等** |
| 4 | 一貫性と、線形化可能性の検査器 | R = 1、W = 1 で、96.4% が崩れる。**R + W > N でも、R = 1、W = 3 で 25.5% が崩れる** |
| 5 | 分断 | CP の分断中の成功率 60%(少数派 0%)。AP は 100% だが、9 キーで競合、LWW で 9 件が失われる |

### つまずいた点と、確かめられなかったこと

1. **演習3: φ 検出器が、固定のタイムアウトに、勝てなかった**。当初は、勝つと予想した。**仮説**(間隔の裾が重く、正規分布の仮定が合わない)は、**別の分布で、確かめていない**。φ 検出器の、本来の利点(環境の変化への適応)は、定常な分布の、この実験では、見えない。**論文の主張を、この実験が、否定するものでは、ない**。
2. **演習2 C(TrueTime 風)は、ほぼ自明なモデル**だった(待ち時間は、式から、ちょうど 2ε)。実際のシステムの挙動(ε の、時間変動、時計の、故障)は、含まない。構造の理解のための、数値である。
3. **演習4: R = 2、W = 2 の、0.4% の違反の原因は、推測**(進行中の書き込みに関する、同じ理由)で、個別の履歴を取り出して、確認していない。
4. **演習4: バージョンの割り当てが、現実より、単純**(開始の順に、全体で一意)。**実際の、複数コーディネータが競合する場合は、さらに崩れうる**と思われるが、**確かめていない**。
5. **演習5の、「競合」の数は、乱数の種に依存する**(1 つの種のみ)。傾向を見るものである。
6. **演習1: ベクタークロックの、切り詰めや、サーバーごとの工夫**は、**実装していない**(本文での言及は、一般的な知識)。
7. **FLP、CAP の証明は、この講義では、再現していない**。主張の、正確な形を、述べ、**誤解**を、避けることに、集中した。

## 9. 博士レベルの論点

答えが定まっていない問い。口頭試問でも議論する。

1. **時間の、本質的な不確かさ**: TrueTime は、ハードウェアで、ε を小さくする。**ハードウェアなしで、ε を、安全に見積もる**ことは、できるか。**時計の、故障**(ε の保証が、破れる)は、どう扱うか。
2. **一貫性の階層の、細かさ**: 線形化可能性と、結果整合性の間に、**多数のモデル**(因果、PRAM、セッション)がある。**アプリケーションの、不変条件**から、**必要最小限のモデル**を、導く方法は、あるか(「不変条件の確認」、CALM 定理)。
3. **CALM 定理**(Hellerstein ら): **単調な計算**は、調整なしで、一貫して計算できる。**どこまで、調整を、避けられるか**。CRDT(競合のない、複製されたデータ型)は、その実装。
4. **故障検出の、理論と実務**: Chandra と Toueg の、理論(完全性、正確性)と、実務のタイムアウトの、間の、**ギャップ**。**裾が重い**遅延(演習3)を、**どう、モデル化**するか。
5. **CAP の、限界と、それを超える議論**: CAP の「A」は、弱い定義。**実用上の、可用性と、遅延**の、**より精密な定式化**(PACELC、「harvest と yield」)は、あるか。
6. **線形化可能性の、コスト**: 線形化可能な読み書きは、**少なくとも、1 回の往復の、遅延**(多数派への)が、要る、という下限は、**どう示される**か。**ローカルな読み**を、可能にする仕組み(リース、時刻)と、その**危険**(時計の、ずれ)は。
7. **ビザンチン故障の、現実性**: 多くの、データセンター内のシステムは、**クラッシュ故障のみ**を、仮定する。**ビット反転、バグ、悪意**は、どこまで、無視できるか。ブロックチェーンは、**ビザンチンを、許す代わりに、何を失った**か。
8. **観測の、限界**: 分散システムの、**テスト**(Jepsen など)は、**履歴を記録し、一貫性モデルに、照らして、検査する**(演習4 のように)。**検査は、見つけた違反だけを、示す**。**違反がない、ことの証明は、できない**。**形式手法**(TLA+、モデル検査)は、どこまで、補えるか。

## 11. まとめ

- 複数の計算機では、**部分的な故障**、**共有の時計がない**、**遅延に上限がない**。応答がないとき、**届かなかった、処理済み、遅い、落ちた**の、どれか、分からない。
- **物理時計は、ずれる**。LWW は、時計のずれと同程度以下の間隔で、**後の書き込みを、静かに失う**(演習2: σ = 1 ms、Δ = 0.5 ms で 36%)。
- **happened-before** は、因果だけで、順序を定義する。**Lamport 時計**は、a → b ⇒ L(a) < L(b) だが、**逆は成り立たない**(演習1: **約 11% は、並行**)。**ベクタークロック**は、**正確**だが、**プロセス数に比例して、重い**。**HLC** は、物理時刻に近く、**因果的な順序**を守る(0%)。**TrueTime** は、不確かさを区間で表し、**待つ**(約 2ε)。
- **故障検出**は、**速さと、正確さの、トレードオフ**(演習3: 誤検出 715 → 0、検出 100 → 2,950 ms)。**裾の重い遅延**では、**平均ではなく、裾を、実測して決める**。
- **2 人の将軍**: 失われうる通信では、確定的な合意は、作れない。**FLP**: **非同期**で、1 つの故障があるだけで、**必ず終わる**合意は、保証できない(**安全性は、守れる**。部分同期、乱数、検出器で回避)。
- **一貫性モデル**: 線形化可能性 > 逐次 > 因果 > セッション > 結果整合性。**R + W > N は、「完了した書き込みを、読める」だけ**で、**線形化可能性は、保証しない**(演習4: R = 1、W = 3 で 25.5% が崩れた)。
- **CAP**: **分断の間**、**線形化可能性と可用性は、両立しない**。分断は、選べない。**何を諦めるか**を選ぶ(演習5: CP は少数派を拒否、AP は競合を作る)。**PACELC**: 通常時にも、**遅延と一貫性の、トレードオフ**がある。
- **何が測れて、何が測れなかったか**を、区別する。数値は、すべてモデルの結果で、**確かめられていない仮説**は、§8 に書いた。

次回(第13回)は、**合意と複製**。FLP の限界の中で、**Paxos と Raft** は、どう、複数のノードに、同じ順序で、操作を、実行させるのか。
