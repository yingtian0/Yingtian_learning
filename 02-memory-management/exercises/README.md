# 第2回 演習

ex1〜ex5 は C(標準ライブラリ、POSIX のみ)。ex6 は Go。macOS(Apple Silicon)で動作を確認した。Linux でも動くように書いてあるが、**Linux での実行は未確認**。

```bash
cd 02-memory-management/exercises
```

## 進め方

第1回と同じ。

1. **実行前に予想を書く**。
2. 実行して比べる。外れたら、なぜ外れたかを調べる。
3. 結果と考察を自分のノートに残す。

計測の注意:

- 他の重いプロセスを止める。各計測は3回以上行い、ばらつきを見る。
- **ex2 と ex5 は、実際にメモリを使う**(ex2 は 256MiB、ex5 は最大 256MiB)。空きメモリが少ない環境では、数値を小さくしてから実行する。

## 演習1: アドレス空間を観察する

[ex1_address_space.c](ex1_address_space.c)

```bash
cc -O0 -o ex1 ex1_address_space.c && ./ex1 && ./ex1
```

**課題**

1. 出力を、アドレスの小さい順に並べ、講義の図1の配置と照らし合わせる。
2. 2回の実行で、どの領域のアドレスが変わるか。変わらない領域はあるか。その理由を考える。
3. `malloc(100)` と `malloc(64MB)` のアドレスが、大きく離れているのはなぜか。
4. 実行中に、別の端末で対応表を見る。
   - macOS: `vmmap <pid>`(プログラムは 5 秒待つ)
   - Linux: `cat /proc/<pid>/maps`
5. 発展: 変数 `g_bss` と `g_init` が、実行ファイルのサイズに与える影響を確認する(`g_bss` を 100MB にしても、ファイルサイズは増えない)。

## 演習2: 遅延割り当て

[ex2_lazy_allocation.c](ex2_lazy_allocation.c)

```bash
cc -O1 -o ex2 ex2_lazy_allocation.c && ./ex2
```

**課題**

1. 1 GiB の `mmap` の直後に、RSS が変わらないことを確認する。
2. 256MiB に初めて触れたとき、フォルトの回数が、ページ数と一致するか。ページサイズが 4KB の環境では、何回になると予想するか。
3. 同じ範囲に何度も書き直したとき、1ページあたりの時間がどう変わるか。**macOS では、フォルトが増えないのに遅いパスがある**。これは、本講義で原因を特定できていない現象である。調べて、仮説を立てよ。
4. Linux で実行できるなら、同じ現象が出るか比べる。`perf stat -e page-faults,dTLB-load-misses ./ex2` も使う。
5. **改造**: `p[i * page] = 1`(書く)を `sum += p[i * page]`(読む)に変えて、RSS とフォルトの回数を比べる。読むだけでも、物理メモリは使われるか。
6. **改造**: `MAP_POPULATE`(Linux)や `madvise(MADV_WILLNEED)` を使うと、フォルトのタイミングがどう変わるか。

## 演習3: TLB の届く範囲

[ex3_tlb_reach.c](ex3_tlb_reach.c)

```bash
cc -O2 -o ex3 ex3_tlb_reach.c && ./ex3
```

**課題**

1. 「分散」と「連続」の差が、いくつのページ数から現れるか。自分の CPU の TLB 構成(公式資料や解析記事で調べる)と比べる。
2. ページサイズが違う環境(Linux の x86-64 は 4KB)では、差が現れるページ数は、どう変わると予想するか。
3. **改造**: 分散配置を、巨大ページで確保して再測定する。
   - Linux: `madvise(p, size, MADV_HUGEPAGE)`。または `mmap` に `MAP_HUGETLB`(事前の設定が必要)
   - 差が縮むか。
4. **改造**: 各ページの中の位置を、全て同じオフセットにして(`(i % lines_per_page)` をやめる)再測定する。キャッシュのセットの衝突で、結果が変わるか(第1回の図2を参照)。
5. 発展: ページ数 N が、最後の階層の TLB を超えたとき、ページウォークのコストがどれくらいか、2つの差から見積もる。

## 演習4: 自作 malloc

[ex4_mini_malloc.c](ex4_mini_malloc.c)

```bash
cc -O2 -o ex4 ex4_mini_malloc.c && ./ex4
```

**課題**

1. テスト1(正しさ)の出力を確認する。コードの `mm_free` から、結合の処理を一時的に外すと、何が起きるか。
2. テスト2(外部断片化)で、「64B の方を解放」した後の最大の空きは 992B だった。この値が、なぜ 992B になるのかを計算で確かめる(1組 = 64B + 1024B + ヘッダ 2 個 = 1152B。アリーナの 4 MiB からヘッダ 1 個分を引いた値を、1152 で割った余りを求める)。
3. **改造**: first-fit を **best-fit**(入る中で最小の空きを選ぶ)に変える。テスト2の断片化の結果と、速度は、どう変わるか。
4. **改造**: 空きリストを、サイズクラスごとに分ける(例: 16, 32, 64, …, 4096 B)。速度は、システムの `malloc` にどこまで近づくか。内部断片化は、どれだけ増えるか。
5. **改造**: ヘッダを小さくする(サイズだけを持たせ、アドレス順の隣は、サイズから計算する)。結合の処理は、どう変わるか。
6. 発展: `pthread` で複数スレッドから呼ぶと壊れることを確認する。ロックを1つ付けた場合と、スレッドごとのアリーナを持たせた場合で、速度を比べる。

## 演習5: fork と Copy-on-Write

[ex5_fork_cow.c](ex5_fork_cow.c)

```bash
cc -O1 -o ex5 ex5_fork_cow.c && ./ex5
```

**課題**

1. `fork()` の時間と、常駐メモリの関係を、グラフにする。**今回の環境では、ばらつきが大きく、傾向は弱かった**。測定回数を増やして(各条件 10 回の中央値など)、傾向がはっきり出るか確認する。
2. 子が読むだけのとき、フォルトは起きるか。macOS と Linux で、結果が異なると予想されるが、実際はどうか。
3. 子が書いたときの 1 ページあたりの時間が、演習2の初回(ゼロ埋め)と比べて、どうか。差の理由を考える。
4. **改造**: 子が書くページを、全体の 10%、50%、100% と変えて、メモリ使用量の増え方(RSS の合計)を調べる。Redis の例(講義 8.3)との対応を考える。
5. **改造**: `fork()` の直後に `exec()` を呼ぶ場合と、`posix_spawn` を使う場合で、時間を比べる。巨大な常駐メモリのプロセスで、差が出るか。

## 演習6: Go のメモリ確保

[ex6_go_alloc/](ex6_go_alloc/)

```bash
cd ex6_go_alloc
go run .
go build -gcflags='-m' . 2>&1 | grep -E 'moved to heap|escapes to heap|does not escape'
```

**課題**

1. 各関数の確保回数(allocs/op)が、コンパイラの出力(`moved to heap` など)と一致するか確認する。
2. `toInterface` の引数を、定数(`toInterface(7)` ではなく、コード中に直接書いた `point{1, 2}`)にすると、確保が 0 になる。その理由を調べる(コンパイラが、読み取り専用の静的データを使う)。
3. `makeSliceDynamic(16)` の確保回数が、Go のバージョンで変わるか。可能なら、複数のバージョンで試す。
4. **改造**: ヒープの確保を `sync.Pool` で再利用して、GC の回数(`runtime.NumGC`)と、`HeapIdle` の変化を見る。
5. **改造**: `GOMEMLIMIT=100MiB go run .` で実行する。256MiB を保持するコードで、何が起きるか(`GOMEMLIMIT` は、ソフトな目標であり、保持しているメモリは返せない)。
6. **改造**: `GODEBUG=gctrace=1 go run .` で、GC のログを見る。
7. 発展: `go tool pprof` で、ヒープのプロファイルを取り、確保の多い箇所を特定する。

## 参考結果(Apple M5、macOS、ページサイズ 16KB、メモリ 16GB)

| 演習 | 結果 |
|---|---|
| 1 | ヒープ、mmap、スタックのアドレスが、実行のたびに変わる |
| 2 | 1 GiB 確保で RSS 変化なし。256MiB に初めて触れるとフォルト 16384 回(1ページ約 2〜3µs)。2回目のパスは約 1.1〜1.3µs/ページ、3回目以降は約 7〜10ns/ページ |
| 3 | 分散配置は、128 ページまでは連続配置と同じ。256〜2048 ページで約 3 倍。4096 ページ以降は約 9〜12 ns |
| 4 | 結合は正しい。断片化で空き 228KB でも 4KB が確保できない。速度は、システムの約 16 倍遅い(300 ns/回 対 18 ns/回) |
| 5 | fork は 0MB で約 0.5〜0.7ms、256MB で 0.9〜2.4ms(ばらつき大)。子の読み込み約 8〜10ms、書き込み(COW)約 47〜51ms |
| 6 | `sumByValue` 0、`newPointer` 1、`toInterface(7)` 1、`makeSmallSlice` 0。GC 後も HeapIdle が 259MB。`FreeOSMemory` で返却 |

数値は、環境、OS、Go のバージョン(1.26.5)で変わる。講義本文の §14 に、測定でつまずいた点を記した。
