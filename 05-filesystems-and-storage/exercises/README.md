# 第5回 演習

ex1、ex2 は C(POSIX)。ex3〜ex5 は Go。macOS(Apple Silicon、APFS、内蔵 SSD)で動作を確認した。Linux でも動くように書いてあるが、**Linux での実行は未確認**。

```bash
cd 05-filesystems-and-storage/exercises
```

## 進め方

第1〜4回と同じ。実行前に予想を書き、実行して比べ、外れたら理由を調べる。各計測は3回以上行う。

**注意**

- ex2 は、数秒間、同期の書き込みを繰り返す。ex5 は、512 MiB のファイルを作り、ストレージに負荷をかける。**他の重い作業を止めてから実行する**。
- **ex3 は、子プロセスに `SIGKILL` を送る**(自分で起動した子だけ)。電源断ではない。
- 作るファイルは、一時ディレクトリ(`TMPDIR`)に置かれ、終了時に消える。空き容量が足りない環境では、ex5 の `fileSize` を小さくする。

## 演習1: inode、リンク、fd、スパースファイル

[ex1_inode_links.c](ex1_inode_links.c)

```bash
cc -O1 -Wall -Wextra -o ex1 ex1_inode_links.c && ./ex1
```

**課題**

1. 出力から、ハードリンクが**同じ inode、リンク数 2** になることを確認する。シンボリックリンクの**サイズが、パス名の長さ**になることを確認する(`readlink` で中身を読む)。
2. 開いたまま `unlink` したファイルが、`fstat` でリンク数 0、でも読めることを確認する。**別の端末で `ls -l /dev/fd/` や `lsof` で、削除済みのファイルが見えるか**調べる(Linux)。
3. **改造**: ハードリンクを、**別のファイルシステム**(例えば `/tmp` が別の場合)との間で作ろうとする。何というエラーが出るか。
4. **改造**: スパースファイルを、`cp` でコピーする。コピー先も、スパースのままか(`du` で確認する)。`cp --sparse=always`(Linux)や、`dd` との違いも見る。
5. **改造**: 小さなファイル(1 バイト)を 10 万個作り、`df -i` と `df -h` の変化を見る。使用ブロックは、ファイルサイズの合計の何倍か。
6. **改造**: `fork` を使い、親子が、同じ fd で `write` するときの、オフセットの動き(出力が上書きされるか、追記されるか)を確認する(第3回の fork と、本回の「開いたファイル」の関係)。
7. 発展: `O_APPEND` で開いたファイルに、複数のプロセスから `write` する。`O_APPEND` なしと比べて、出力が混ざったり上書きされたりしないことを確認する。

## 演習2: 同期のコスト

[ex2_fsync_cost.c](ex2_fsync_cost.c)

```bash
cc -O2 -Wall -Wextra -o ex2 ex2_fsync_cost.c && ./ex2
```

**課題**

1. 4つの方式(`write` のみ、`fsync`、`F_FULLFSYNC`、まとめて同期)の、平均、p50、p99、最大を表にする。3回測って、ばらつきを見る。
2. **`fsync` と `F_FULLFSYNC` の比**を計算する。この Mac では約 114 倍だったが、あなたの環境ではどうか。
3. **Linux で実行できるなら**、`F_FULLFSYNC` の代わりに `fdatasync` が使われる。macOS の `fsync` より遅いか。`strace -T -e trace=fsync,fdatasync` で、1回あたりの時間を見る。
4. **改造**: 書き込みのサイズを、512 バイト、4KB、64KB、1MB と変えて、`F_FULLFSYNC` の時間が、サイズにどれくらい依存するか見る。同期のコストは、サイズより回数に支配されるか。
5. **改造**: `O_SYNC`(Linux)、`O_DSYNC`、`fcntl(F_NOCACHE)` で開いたファイルへの `write` を測る。
6. **改造**: **group commit** を実装する。複数のスレッドが、書き込みを溜めて、1回の `fsync` で、まとめて永続化する。スレッド数が増えると、1秒あたりの書き込み件数が、どう伸びるか。
7. 発展: **新しく作ったファイルの `fsync` の後に、親ディレクトリを `fsync` するかしないか**で、時間がどう変わるか。ディレクトリの `fsync` は、どのメタデータを書くか(Linux の `strace` で確認)。

## 演習3: 安全なファイルの置き換え

[ex3_atomic_replace/](ex3_atomic_replace/)

```bash
cd ex3_atomic_replace
go run . demo naive
go run . demo safe
```

**課題**

1. naive と safe の結果を比べる。naive が、**途中で死ぬだけで壊れる**ことを確認する。
2. `time.Sleep(450 * time.Millisecond)` を変えて、強制終了のタイミング(早い、遅い)を変える。safe では、どのタイミングでも、古い内容が残るか。最後に近いタイミング(新しい内容を書き終え、`rename` の直前、直後)では、どうなるか。
3. **このデモが確認できないこと**を、自分の言葉で説明する。電源断を再現するには、何が必要か(仮想マシンの強制停止、`dm-flakey`、専用のツール、などを調べる)。
4. **改造**: safe の `f.Sync()` を消す。`SIGKILL` のデモの結果は、変わるか。なぜか。**電源断では、どう変わるはずか**。
5. **改造**: safe の `syncDir` を消す。同様に考える。
6. **改造**: **別のファイルシステム**に、一時ファイルを作って `rename` する。何というエラーが出るか(`EXDEV`)。なぜ、一時ファイルは、同じディレクトリに作るべきか。
7. 発展: Go の `renameio` や、`natefinch/atomic` などのライブラリの実装を読み、本回の手順と比べる。

## 演習4: 小さな LSM-tree

[ex4_mini_lsm/](ex4_mini_lsm/)

```bash
cd ex4_mini_lsm && go run .
```

ファイル構成: `lsm.go`(ストア本体)、`main.go`(5つのデモ)。

**課題**

1. 5つのデモの出力を読み、本文 §7.5 の表と比べる。
2. **コードを読む**: `parseRecords` が、どんな状態を「壊れた」と判定するか。`Open` が、WAL を再生した後、壊れた末尾を**切り詰める**理由は何か(切り詰めずに、追記を続けると、何が起きるか)。
3. **改造**: WAL の**途中**のレコードを壊す(1 バイト書き換える)。再起動すると、どうなるか。後ろの(正常な)レコードも失われるか。これを、設計として、どう扱うべきか(クイズ 40 を参照)。
4. **改造**: `flush` の中の、「SSTable を永続化した後に、WAL を消す」順序を、逆にする(先に WAL を消す)。間でクラッシュ(`panic` を入れる)したときに、データが失われることを確認する。
5. **改造**: `compact` の、「新しい SSTable を永続化した後に、古いものを消す」順序を、逆にして、同様に確認する。
6. **改造**: コンパクションの方針を変える。**サイズ階層型**(同じ大きさの SSTable が 4 個溜まったら、マージして、1つ大きいものにする)にして、書き込み増幅を比べる。読み出し(SSTable の数)は、どうなるか。
7. **改造**: ブルームフィルタの、1 キーあたりのビット数を、5、10、20 と変えて、偽陽性率と、メモリ使用量を比べる。
8. **改造**: SSTable に、**ブロック単位の CRC** を付け、読み出し時に検証する。ディスクの破損(1 ビット反転)を検出できることを確認する。
9. **改造**: ストアにスレッド安全性を持たせる(ミューテックス)。複数の goroutine から、`Put` と `Get` を同時に呼ぶ。`go test -race` で確認する。第4回の内容との接続。
10. 発展: 範囲検索(`Scan(start, end)`)を実装する。複数の SSTable とメモリテーブルを、**k-way マージ**で、キー順に返す。

## 演習5: キュー深さと IOPS

[ex5_io_queue_depth/](ex5_io_queue_depth/)

```bash
cd ex5_io_queue_depth && go run .
```

**課題**

1. キュー深さごとの IOPS とレイテンシを、グラフにする。**IOPS が頭打ちになる点**はどこか。
2. 各点で、**Little の法則**(QD = レイテンシ × IOPS)を検算する。
3. **ページキャッシュの影響を確認する**: `F_NOCACHE`(macOS)の設定を消して実行する。IOPS は、どれくらい上がるか。`F_NOCACHE` で、キャッシュを避けられていると言える根拠は何か。
4. **Linux で実行できるなら**: `O_DIRECT`(ブロックサイズに揃えたバッファが必要)で開く改造をする。あるいは、`fio` で同じ測定を行う。
   ```bash
   fio --name=randread --filename=/tmp/fio.dat --size=512M --rw=randread --bs=4k \
       --iodepth=1 --ioengine=libaio --direct=1 --runtime=5 --time_based
   # --iodepth を 1, 4, 16, 64 と変える
   ```
5. **改造**: ブロックサイズを、4KB、16KB、64KB、1MB と変えて、IOPS と MB/s の関係を見る。どのサイズで、MB/s が最大になるか。
6. **改造**: **書き込み**(ランダム 4KB)で、同じ測定をする。読み込みと比べて、IOPS とレイテンシ(特に p99)は、どう違うか。GC の影響が見えるか(長時間、書き続ける)。
7. **改造**: 同じファイル内の、**順次**アクセスのキュー深さを変えて測る(1 MiB ずつ、QD 1〜8)。順次では、並列度が効くか。
8. 発展: ファイルシステム経由ではなく、ブロックデバイスに直接アクセスする(root 権限が必要。**他のデータを壊さないよう、専用のデバイスでのみ行う**)。ファイルシステムのオーバーヘッドが、どれくらいか。

## 参考結果(Apple M5、macOS、APFS、内蔵 SSD、Go 1.26.5)

| 演習 | 結果 |
|---|---|
| 1 | ハードリンクは同じ inode(リンク数 2)、シンボリックリンクのサイズは 65(パス名の長さ)。開いたまま `unlink` しても読める。1 GiB のスパースファイルが 4096 バイトだけ使用。`dup` はオフセットを共有 |
| 2 | `write` 3.7 µs、`fsync` 33.0 µs、`F_FULLFSYNC` 3,748 µs(`fsync` の約 114 倍)。まとめて書いて最後に 1 回同期すると 3.1 µs/回 |
| 3 | naive: 強制終了後、3 MiB の壊れたファイル。safe: 古い内容 4 MiB が残った。**電源断は再現していない** |
| 4 | 不一致 0。切れた WAL の末尾を検出し、999 件を再生。ブルームフィルタで 250,271 → 2,070 回。書き込み増幅 3.62 倍。同期: なし 605k/s、100 件ごと 419k/s、fsync 59k/s、F_FULLFSYNC 275/s |
| 5 | QD 1: 15,668 IOPS(63.7 µs)、QD 64: 199,641 IOPS(316.6 µs)。順次読み込み 6,204 MB/s |

数値は環境で変わる。本文の §9 に、測定でつまずいた点、確認できていない点を記した。
