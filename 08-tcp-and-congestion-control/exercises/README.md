# 第8回 演習

ex1、ex2、ex4 は Go(標準ライブラリのみ)。ex3 は C(macOS 専用)。macOS(Apple Silicon)で動作を確認した。**Linux での実行は未確認**。

```bash
cd 08-tcp-and-congestion-control/exercises
```

## 進め方

第1〜7回と同じ。実行前に予想を書き、実行して比べ、外れたら理由を調べる。

**この環境の制約**: 損失や遅延を、人工的に作る(`tc netem`、macOS の `dnctl`/`pfctl`)には、管理者権限が要る。**実際の TCP が、損失や遅延のもとで、どう振る舞うかは、この演習では測れていない**。そのため、ex4 は、**シミュレータ**にした。

**注意**

- ex1 は、ループバックにだけ接続する。`lsof` は、自分のプロセスの接続だけを表示する。
- ex4 は、実際の TCP の測定ではなく、簡易モデルのシミュレーションである。**結果を、実際の振る舞いとして引用しない**。
- **システムの設定(`sysctl` の書き込み、`pfctl` など)を、変更しない**。読み取りだけ。

## 演習1: 接続の状態と、接続のコスト

[ex1_tcp_states/](ex1_tcp_states/)

```bash
cd ex1_tcp_states && go run .
```

**課題**

1. A の出力から、接続の各段階の状態を確認する。**クライアントが先に close したとき、サーバー側が `CLOSE_WAIT` になる**ことを確認する。
2. B の結果を、表にする。**サーバーが先に close したときだけ、`SO_REUSEADDR` なしで bind できない**ことを確認する。理由を、TIME_WAIT の位置から説明する。
3. C の、新しい接続と使い回しの比を記録する(3回測って、ばらつきを見る)。ループバックの RTT が、ほぼ 0 であることを考えて、**実際のネットワーク**(RTT 20 ms)での、1 リクエストの時間を見積もる。
4. **改造**: `CLOSE_WAIT` を、**わざと作る**。サーバーが、`accept` した接続を、`close` せずに放置する。クライアントが閉じた後、`lsof` で、`CLOSE_WAIT` が残り続けることを確認する。
5. **改造**: 接続を 1,000 本張って、すべて閉じた後、`lsof` と、(使える環境なら)`netstat -an` で、状態の数を数える。
6. **改造**: **`SetLinger(0)`**(RST で閉じる)を使った場合と、使わない場合で、`bind` の結果が、どう変わるか。RST で閉じると、TIME_WAIT は、残るか。
7. **改造**: 長さを先頭に付けたメッセージで、1 つの接続の上に、**パイプライン**(応答を待たずに、複数のリクエストを送る)を実装する。1 つずつ待つ場合と、スループットを比べる。(第6回のキュー深さと同じ考え方。)
8. 発展: **Linux で実行できるなら**、`ss -tan` と `ss -ti` で、同じ観察をする。FIN_WAIT_2 と TIME_WAIT も、見えるはずである。

## 演習2: Nagle と遅延 ACK

[ex2_nagle_delayed_ack/](ex2_nagle_delayed_ack/)

```bash
cd ex2_nagle_delayed_ack && go run .
```

**課題**

1. 3つの方式の平均を比べる。**この環境では、40 ms の停止が再現しない**ことを確認する。
2. 繰り返しの回数を増やして(1,000 回)、**最大値**(外れ値)に、停止のような値が現れるか確認する。
3. **Linux で実行できるなら**、同じ実験をする。`net.ipv4.tcp_delack_min` などと関係する、停止が現れるか。(**システムの設定は、変更しない。**)
4. **改造**: リクエストを、3 回の write(4 バイト、50 バイト、50 バイト)で送る。停止は、どう変わるか。
5. **改造**: サーバー側で、リクエストを受け取った直後に、**応答を返さず**、少し待ってから返す(遅延)。クライアントが、Nagle あり/なしで、どう変わるか。
6. **改造**: `net.Buffers`(Go の `writev` 相当)で、ヘッダと本体を、1 回のシステムコールで送る。2 回の write と比べる。
7. 発展: **ネットワークの往復時間が大きい環境**(自分の管理下の、別のマシンへ)で、この実験を行う。Nagle と遅延 ACK の影響は、大きくなるか。

## 演習3: TCP の内部の状態(macOS 専用)

[ex3_tcp_info.c](ex3_tcp_info.c)

```bash
cc -O2 -Wall -Wextra -o ex3 ex3_tcp_info.c && ./ex3
```

**課題**

1. A の、接続直後の cwnd が、MSS の **10 倍**であることを確認する(初期ウィンドウ 10、RFC 6928)。
2. 64 MiB を送る間の cwnd の成長を、グラフにする。**4,194,240 バイトで頭打ち**になる理由を調べる(送信バッファの上限、`net.inet.tcp.sendspace` などの `sysctl` を、読み取りだけで確認する)。
3. B の、フロー制御の観察を、表にする。**相手のウィンドウが縮んでいく様子**と、**送信側が約 0.7 MB で止まる**ことを確認する。0.7 MB が、送信バッファと受信バッファの合計であることを、`SO_SNDBUF`、`SO_RCVBUF` の値(`getsockopt`)で、確かめる。
4. **改造**: 受信側が `read` しない時間を、0.1 秒、1 秒、5 秒と変える。送信側が、止まるまでに送れる量は、変わるか。
5. **改造**: `SO_RCVBUF` を、小さく(8 KB)設定して、同じ実験をする。送信側が止まるまでに送れる量が、どう変わるか。**ウィンドウ拡大が、小さなバッファでは、使われなくなる**(拡大率が下がる)ことを確認する。
6. **改造**: 受信側が、**少しずつ**(1 秒に 1 KB ずつ)読む。ウィンドウの推移は、どうなるか。**愚かなウィンドウ症候群**の回避が、見えるか。
7. **改造**: `TCP_NODELAY` と `TCP_NOTSENT_LOWAT` を設定して、`tcpi_snd_sbbytes`(送信バッファの中のバイト数)が、どう変わるか。
8. **Linux で実行できるなら**: `TCP_INFO`(構造体が違う)で、同じ観察をする。`ss -ti` の出力と比べる。

## 演習4: 輻輳制御のシミュレータ

[ex4_cc_sim/](ex4_cc_sim/)

```bash
cd ex4_cc_sim && go run .
```

**重要**: 簡易モデルである。**実際の TCP の測定ではない**。

**課題**

1. **A(のこぎり波)**: cwnd のグラフを描く。周期(約 31 秒)を、BDP(416 パケット)と、RTT から、**理論的に見積もる**(1 RTT あたり +1 パケット、416 パケット増えるのに、416 RTT。RTT は、キューの遅延を含めて、50〜100 ms)。見積もりと、シミュレーションの周期を比べる。
2. **B(バッファ)**: Reno の利用率が、バッファの大きさで、どう変わるかを、グラフにする。**バッファ = BDP で、利用率がほぼ 100% になる**ことを確認する。
3. **バッファの経験則の検証**: **複数のフロー**(10 本の Reno)が、ボトルネックを共有するとき、バッファ = BDP ÷ √10 でも、利用率が高いか。(**`Config` に、フローを 10 本並べる。**)Appenzeller らの結果と、比べる。
4. **C(損失)**: Reno のスループットと、Mathis の式を、グラフにする(両対数)。傾き(-1/2)が、合っているか。
5. **改造**: **RTT を、20 ms、100 ms、200 ms** に変えて、同じ損失率での、Reno のスループットを比べる。Mathis の式のとおり、RTT に反比例するか。
6. **改造**: **タイムアウト**を実装する。窓の全部のパケットが失われたとき(または、一定時間 ACK がないとき)、cwnd を 1 に戻し、RTO を倍にする。高い損失率(5%)での、Reno のスループットが、どう変わるか。
7. **改造**: **簡易 BBR を、実際の BBR に近づける**。ProbeRTT(10 秒ごとに、200 ms の間、cwnd を 4 に絞って、RTprop を測り直す)を実装する。Reno との共存の結果は、どう変わるか。**BBR v1 と v2 の違い**(損失への反応)を調べる。
8. **改造**: **ECN** を実装する。キューが、あるしきい値を超えたら、パケットを捨てる代わりに、「輻輳」の印を付け、送信側が、cwnd を縮める。バッファが深くても、遅延が小さく保たれるか。(DCTCP の考え方を、簡易に試す。)
9. 発展: **AQM**(CoDel の簡易版)を実装する。バッファが深くても、バッファブロートが抑えられることを確認する。
10. 発展: **自分の管理下の、実機の環境**(Linux で `tc netem` が使える環境)で、このシミュレータの予測を、実際の `iperf3` の結果と比べる。**どこが、合っていて、どこが違うか**。
